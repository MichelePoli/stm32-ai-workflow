\section*{Summary}\label{section:summary}

Deploying a neural network on a resource-constrained STM32 microcontroller is a multi-stage process that requires expertise in both machine learning and embedded systems. In a typical manual workflow, an engineer configures the peripheral hardware with STM32CubeMX, converts and quantizes the model with STEdgeAI, fine-tunes or compresses the network to satisfy Flash and RAM budgets, and finally patches the generated C code to integrate the inference engine into the firmware project. Each step involves a separate tool with its own command-line interface, configuration format, and failure mode. Engineers usually connect these steps through hand-crafted shell scripts or manual copy-paste operations. This fragmented approach pushes iteration cycles beyond four hours, even for experienced developers. The friction raises the barrier to entry, as practitioners must be fluent in TensorFlow, embedded C, and ARM toolchains simultaneously.

Large Language Models offer a natural interface for this kind of multi-tool orchestration: they can parse free-text intent, select parameters, invoke external tools, and interpret error messages. A single LLM call alone, however, is not reliable enough for multi-step engineering tasks. Isolated chat queries cannot maintain state across tool invocations, route to domain-specific processing, or provide a human engineer with a checkpoint to review intermediate decisions before they become irreversible.

This thesis presents a multi-agent MLOps orchestration framework that addresses these limitations. We decomposed the deployment pipeline into a directed graph of specialized nodes. State passes explicitly between nodes through a typed schema, ensuring conditional routing, persistence, and supervised handoffs at defined decision points. The system translates a single natural language prompt, such as \textit{``Deploy a gesture classifier on STM32H7 with high compression''}, into a verified and compilable firmware project with almost zero manual intervention.

\subsection*{System Architecture}

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.95\textwidth]{chap3/figures/topDownArchitecture.png}
    \caption{Five-layer system architecture of the proposed framework, from the IDE interface down to the centralized GPU inference cluster.}
    \label{fig:summary_architecture}
\end{figure}

As illustrated in Figure~\ref{fig:summary_architecture}, the framework is organized across five layers. The \textbf{IDE Layer} hosts a custom Visual Studio Code extension that presents a streaming chat interface directly inside the editor. The \textbf{API Gateway Layer} consists of a FastAPI server (running in the \texttt{langgraph-app} Docker container) that exposes a single \texttt{/stream} endpoint, retrieves the user's long-term profile from Redis, constructs the initial graph state, and pipes back structured JSON events in real time. The \textbf{Orchestration Layer} is a LangGraph stateful graph whose LLM-based router classifies each incoming message and dispatches it to one of five agentic workflows: Firmware Generation, AI Model Discovery, Model Customization, Firmware-AI Integration, and Web Research. The \textbf{State and Memory Layer} uses a dedicated Redis container in two roles: as the LangGraph checkpointer (persisting the full \texttt{MasterState} at every node transition) and as a per-user long-term profile store that survives across sessions, recording the preferred board, last model, and project paths. The \textbf{Inference Layer} forwards all LLM calls over the network to a centralized NVIDIA Triton Inference Server deployed on the inNuCE Lab Heterogeneous Prototyping Platform (HPP), equipped with an NVIDIA A40 GPU (45~GB VRAM). Triton handles dynamic model loading and GPU memory sharing across concurrent users, keeping the local orchestration containers free of GPU dependencies.

Human-in-the-Loop gates, implemented through LangGraph's \texttt{interrupt()} primitive, allow engineers to approve decisions, redirect searches, or override model choices at defined breakpoints without losing execution context. At critical transitions (before launching a training job or before running the STEdgeAI compiler) the system pauses and asks the developer for explicit confirmation inside the IDE chat, so control never leaves the engineer's hands.

\subsection*{Implemented Workflows}

The Firmware Generation workflow automates STM32CubeMX project initialization without any graphical interface interaction. It uses a pre-seeded IOC template strategy combined with a headless execution environment (\texttt{xvfb-run} virtual framebuffer) to translate the user's natural language description of peripherals and board into a compilable C project in about 30 seconds.

The AI Model Discovery workflow implements a two-tier search: a curated pool of pre-validated STM32-compatible models indexed by task type, and an iterative web search across HuggingFace and GitHub repositories when the curated pool yields no suitable candidate. Once a model is selected, the workflow hands off to STEdgeAI for Flash/RAM analysis and C-code generation. A hardware-aware gating mechanism checks resource constraints and autonomously escalates compression before generating code. If the model still exceeds the target board's limits, the orchestrator pauses and offers the developer two explicit choices.

The Model Customization workflow enables layer-level neural network modification driven entirely by natural language. The agent inspects the loaded model's architecture, retrieves architecture-specific best practices from a RAG pipeline, and rewrites the Keras training script to apply the requested changes: layer freezing, dropout injection, output head replacement, or custom learning rate assignment. A class-mismatch rescue mechanism detects dimension conflicts between the pre-trained model and the target dataset and repairs the final classification layer before training begins. If the user requests hyperparameter optimization, the system integrates with Microsoft Neural Network Intelligence (NNI): trial script, search space definition, and experiment configuration are generated from scratch, while the tuner explores learning rates and batch sizes across multiple trials automatically.

The Firmware-AI Integration workflow scans the X-CUBE-AI output directory, copies the generated inference files into the correct STM32 project locations (\texttt{Core/Src/}, \texttt{Core/Inc/}), patches \texttt{main.c} to wire in the inference call, and verifies build compatibility. The Web Research workflow classifies the user's query intent, executes a DuckDuckGo search, synthesizes the retrieved page content into a grounded answer, and evaluates the output automatically using DeepEval.



\subsection*{Experimental Results}

I evaluated developer productivity by comparing the automated workflow against a KLM-derived manual baseline, constructed from official STMicroelectronics documentation. The end-to-end deployment time dropped from roughly 3.5--4.5 hours to 20--30 minutes, yielding a median $9\times$ speedup. Task-level gains are even sharper. CubeMX project setup went from 20--30 minutes to 30--45 seconds ($40\times$) just by eliminating all GUI interaction. NNI experiment setup dropped from 45--60 minutes to 1--2 minutes ($30\times$) via template-based code generation. Finally, model discovery improved by $24\times$ thanks to the hybrid two-tier search.

Then I validated code quality through a recorded end-to-end session where the customization agent adapted a pre-trained model for a custom dataset. The agent autonomously resolved architectural class mismatches, injected regularization layers, and froze base feature extractors. The modified network converged within the safety cap, achieving over 98\% validation accuracy.

I also evaluated the Web Search workflow using a DeepEval LLM-as-a-Judge paradigm across five technical query types. The retrieval-augmented pipeline consistently surfaced relevant content with a near-zero hallucination rate and perfect faithfulness on procedural queries, confirming its reliability as a grounded research assistant.

Concurrency stress tests pushed the Triton back-end to 15 simultaneous users requesting complex text generation across two models over a 1~Gbps network connection. VRAM occupation stabilized at approximately 37~GB (80\% of A40 capacity) while GPU compute stayed near 100\%, demonstrating that the network link was not a throughput bottleneck.

The architecture is already prepared for the next scale step. Because the orchestration containers are GPU-free, migrating from Docker Compose to Kubernetes requires only replacing the compose manifest with a deployment specification. A horizontal pod autoscaler can then scale the LangGraph layer independently from the Triton server, enabling enterprise teams to share the GPU cluster without constraining the agent layer.
