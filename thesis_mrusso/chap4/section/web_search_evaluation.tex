\section{Web Search Agent: Quality Evaluation with DeepEval}

This section documents the experimental validation of the Web Search Agent (Workflow~4), which combines real-time web retrieval via DuckDuckGo, LLM-based summarisation, and automated quality assessment through the DeepEval framework. The evaluation is presented in two phases: a first campaign conducted with a local Ollama back-end, and a second one after migrating inference to NVIDIA Triton Inference Server.

\subsection{Methodology}

\subsubsection{Evaluation Framework}
Quality assessment relies on \textbf{DeepEval}\footnote{\url{https://github.com/confident-ai/deepeval}}, an open-source library for RAG (Retrieval-Augmented Generation) evaluation. Four metrics were selected for their relevance to technical documentation tasks.

\textbf{Faithfulness} measures factual consistency between the generated summary and the retrieved source documents (range 0.0--1.0, higher is better). \textbf{Answer Relevancy} captures the semantic alignment between the user query and the generated response (range 0.0--1.0, higher is better). \textbf{Contextual Relevancy} evaluates retrieval quality by estimating the proportion of retrieved content genuinely useful for answering the query (range 0.0--1.0, higher is better). \textbf{Hallucination} detects claims in the output that are not supported by retrieved documents (range 0.0--1.0, \textbf{lower} is better; 0.0 means no fabrication detected).

Each metric is computed by an auxiliary \emph{LLM-as-a-Judge}: the same inference infrastructure used for main tasks also drives the evaluation step. This avoids external API dependencies and keeps the entire pipeline self-contained.

\subsubsection{Test Protocol}
Evaluation proceeds through five stages. The user query is classified into one of four categories (\texttt{ai\_model}, \texttt{board\_selection}, \texttt{optimization}, \texttt{documentation}). DuckDuckGo then retrieves the top results for the reformulated query. Raw text is split into paragraph-level chunks of at least 20 characters, which serve as the retrieval context. A local Mistral instance (temperature 0.2) synthesises a concise English summary from those chunks. Finally, DeepEval computes the four metrics synchronously inside a dedicated thread via \texttt{asyncio.to\_thread}, keeping the main event loop unblocked.

\subsection{Phase 1 --- Ollama Back-End (Baseline)}

\subsubsection{Configuration}
The first campaign used \textbf{DeepSeek-R1} (7B parameters, GPTQ-quantised) served by a local Ollama instance at \texttt{http://localhost:11434}. Five representative queries were designed to cover the breadth of requests typical of an STM32 developer: model search, board selection, optimisation guidance, conceptual comparison, and hardware benchmarking.

\subsubsection{Aggregate Analysis}
Contextual Relevancy is the most stable indicator across Phase~1 (mean 0.75, $\sigma$ 0.16), confirming that DuckDuckGo combined with paragraph-level chunking reliably surfaces relevant content. Faithfulness varies more ($\sigma$ 0.22): procedural queries score near 1.00 while exploratory queries drop when the model supplements retrieval with prior knowledge. The Hallucination mean of 0.14 confirms that outright fabrication is infrequent; non-zero cases correspond to hardware prices and part numbers absent from the retrieved context.

A recurring inverse relationship between strict Faithfulness and practical utility was observed. Answers scoring below 0.60 on Faithfulness often contain the most useful material for the developer, while perfectly faithful summaries can read as bare paraphrases of the source. For exploratory queries, Faithfulness alone is a poor proxy for answer quality.

\subsection{Phase 2 --- Triton Inference Server Back-End}

\subsubsection{Motivation for Migration}
The Ollama-based setup worked well as a prototype but presented two structural limits. Ollama loads a single model per process, which is ill-suited for an architecture where three models (Mistral, DeepSeek-R1, gpt-oss-20b) must be selectable at runtime within a fixed VRAM budget. Ollama also offers no built-in mechanism for dynamic model loading and unloading, necessary to prevent out-of-memory errors during concurrent LangGraph workflows on the available 16~GB NVIDIA A4000.

The migration to \textbf{NVIDIA Triton Inference Server} (v2, explicit model control mode) addresses both issues. Triton supports dynamic loading and unloading of model instances via its v2 HTTP API, enabling on-demand model swapping. Each model runs as a \textbf{Python backend} module backed by vLLM with GPTQ quantisation to reduce the memory footprint. The long-term goal is to deploy this configuration on HPP (High Performance Platform) infrastructure, where larger GPU allocations would eliminate the model-swap constraint entirely and allow multiple models to remain resident simultaneously.

\subsubsection{Configuration}
For the Triton-based evaluation, the judge model was switched to \textbf{gpt-oss-20b} (TechxGenus/starcoder2-15b-instruct-GPTQ, 15B parameters), chosen initially for its larger parameter count. The evaluation covered one test query (\textit{``STM32 boards comparison''}) with retrieval context capped at five chunks of 300 characters each, and output capped at 800 characters, to limit prompt-length issues identified during debugging.

\subsubsection{Engineering Challenges}
The migration exposed several technical problems that required iterative debugging.

\paragraph{VRAM exhaustion during model loading.} An \texttt{HTTP 400 Bad Request} error from Triton appeared when loading gpt-oss-20b. The error traced back to vLLM's KV-cache allocation: with \texttt{gpu\_memory\_utilization} set to 0.60, the remaining GPU memory after loading model weights was insufficient for any cache blocks. Raising the value to 0.85 resolved the issue, giving the engine approximately 13.6~GB of usable GPU memory.

\paragraph{Endpoint URL mismatch under proxy prefix.} When Triton is accessed with a URL prefix such as \texttt{/triton/v1} (required for the HPP deployment environment), the internal v2 repository API calls for model loading and unloading resolved to incorrect paths. A \texttt{base\_v2\_url} property was added to \texttt{triton\_client.py} to strip the \texttt{/v1} suffix and reconstruct the correct v2 base path dynamically.

\paragraph{Malformed JSON output from the judge model.} DeepEval expects each LLM-as-a-Judge call to return a valid JSON object. Both models tested produced non-conforming output in distinct ways. DeepSeek-R1 appended Python test code after the JSON block, sequences such as \texttt{def test\_extract()} or full \texttt{import} chains drawn from its training corpus. gpt-oss-20b (StarCoder2) occasionally emitted Chinese text, references to unrelated training examples (Einstein Nobel Prize, Keil5 Chinese tutorials), or Python f-string double braces (\texttt{\{\{...\}\}}) instead of literal JSON. A multi-layer extraction pipeline was built inside the \texttt{\_clean\_json} method: double-brace normalisation, \texttt{<think>} tag removal, nested-JSON regex search, backwards bracket scan, and a final fallback that wraps plain-text responses inside a \texttt{\{"reason":~...\}} envelope to prevent hard crashes downstream.

\paragraph{Stop sequence configuration.} Stop sequences were added to vLLM's \texttt{SamplingParams} inside each model's Python backend. For DeepSeek-R1, sequences including \texttt{```}, \texttt{"""}, \texttt{\textbackslash ndef~}, and \texttt{\textbackslash nA:~} were configured with \texttt{max\_tokens} reduced from 1024 to 512. This reduced but did not fully eliminate appended code, since some generation patterns were not covered by the explicit stop list.

\paragraph{Instruction-following limitations of code-specialised models.} The most significant finding of Phase~2 is that \textbf{StarCoder2-15B is not a suitable LLM-as-a-Judge}. StarCoder2 is designed for code completion, not natural-language instruction following. When presented with DeepEval's structured evaluation prompts, it exhibited context confusion: for the Answer Relevancy verdict step it returned ``I don't understand. Please provide more information'', causing a score of 0.00 due to a missing \texttt{verdicts} key. DeepSeek-R1 was more capable at structured output but required the stop-sequence workaround described above. Neither model matched the reliability of a dedicated instruction-tuned LLM.

\subsection{Discussion and Threats to Validity}

\subsubsection{Interpreting the Score Regression}
The Phase~2 scores do not imply that the Triton system produces worse summaries. They indicate that the selected judge model is unsuitable for the evaluation task. A coding model acting as an evaluator introduces measurement noise that makes results unreliable for Faithfulness, Answer Relevancy, and Hallucination. Contextual Relevancy, which depends on a simpler binary verdict structure, proved more resilient to instruction-following failures.

\subsubsection{Why Triton Despite the Regression}
The migration was not motivated by improving evaluation scores. Its goal is a \textbf{production-ready inference infrastructure} that supports multiple models and, eventually, multiple concurrent users. With Triton's explicit model control mode, the system can swap models within the 16~GB VRAM budget on demand, a capability that Ollama could not provide. On HPP hardware with larger allocations, it becomes possible to keep multiple models resident simultaneously, eliminating model-swap latency and enabling a genuinely instruction-tuned model to serve as the judge without the workarounds described above.

\subsubsection{Threats to Validity}
The same three threats from Phase~1 apply here, with additional considerations. On internal validity, the model-swap mechanism introduces latency (35--40 seconds per load event) acceptable in single-user experimentation but not in production. On external validity, Phase~2 covers only one test query rather than five, so broader conclusions about Triton's effect on answer quality would require a full five-query replication. On construct validity, a code-specialised model acting as an evaluator produces scores that do not correspond to the same underlying construct as those from an instruction-tuned model, making the two phases not fully comparable on Faithfulness and Answer Relevancy.

\subsection{Conclusions}

Phase~1 established that the Web Search Agent, backed by a suitable instruction-following model via Ollama, delivers measurable and interpretable quality metrics. Average Contextual Relevancy of 0.75, Answer Relevancy of 0.57, and a Hallucination rate of 0.14 across five query types confirm that the retrieval and summarisation pipeline is sound. Score variation by query type is predictable: procedural queries score highest on Faithfulness, exploratory queries score higher on Answer Relevancy at the cost of lower Faithfulness.

Phase~2 showed that migrating to Triton introduces significant engineering complexity. The problems encountered, from VRAM allocation errors to JSON parsing anomalies and instruction-following failures, are not intrinsic to Triton but to the judge models available within the current hardware constraints. Contextual Relevancy improved to 1.00, confirming the retrieval pipeline was unaffected. Future iterations should pair Triton with a genuinely instruction-tuned model as the evaluation back-end, reserving code-specialised models for their intended use cases.
