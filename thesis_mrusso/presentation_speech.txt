[Slide 1: Title & Introduction]
Good afternoon everyone. I'm Michele Russo and today I present my thesis: "From IDE to Edge: A Cloud-Native Multi-Agent Framework for Automated Edge AI Deployment on STM32".

[Slide 2: The Core Problem]
Today a real disconnect exists in embedded development.
AI engineers write Python and train large neural networks. 
Embedded engineers write C, fight strict memory limits, and write low-level firmware directly on STM32 hardware.
Pushing a neural network onto a microcontroller is called Edge AI, and it is still a highly manual process. 
Developers must master a fragmented toolchain: STM32CubeMX for hardware configuration, STEdgeAI for model conversion, custom Python scripts for tuning, and manual C integration.
My tests show this pipeline takes an expert over 4 hours, mostly wasted navigating dense GUIs, reading datasheets and debugging tiny misconfigurations.
The answer I propose is to replace that tedious toolchain with a multi-agent AI framework. Instead of clicking through interfaces, the developer writes a simple prompt like: "Generate an STM32H7 project, find a small MobileNet and integrate it into my C code."


[Slide 3: Architecture — The Five Layers]
As shown in this diagram, the framework is organized across five distinct layers.

At the top is the IDE Layer. The developer interacts through a custom VS Code extension that integrates directly into the editor's native chat. By typing @stm32ai in the chat panel, they communicate with the backend container.

Below that is the API Gateway: a FastAPI server that exposes a single streaming endpoint. It receives each message from the extension, retrieves the user's long-term profile from Redis, constructs the initial graph state, and streams back real-time responses.

The core of the system is the Orchestration Layer. I built the entire pipeline using LangGraph, a framework that lets you define workflows as directed, stateful graphs (grafi diretti e con stato). Each node is a specialized Python function and the LLM acts as the orchestrator, deciding which path to follow based on the context and the user's intent.

Then we have the State and Memory Layer. Redis is the backbone of our memory layer. It saves the full execution state enabling Human-in-the-Loop pauses that survive across requests, and stores long-term user profiles across sessions, like preferred board, last model, previous projects.

Finally, at the bottom is the Inference Layer. All LLM calls go to a centralized NVIDIA Triton Inference Server on the lab's remote cluster. 
Triton handles dynamic model loading and shares GPU memory across concurrent users, so the orchestration containers need no GPU at all.


[Slide 4a : LangGraph - Workflows overview ]

Now let me go deeper into the Orchestration Layer.

When a new message arrives, an LLM-based router (running on Mistral via Triton) classifies the user intent and dispatches it to one of three primary workflows (lo invia a uno dei tre flussi di lavoro principali): Firmware Generation, AI Model Discovery,
or Web Research. The remaining 4 workflows are triggered automatically as the pipeline progresses.

The first workflow is Firmware Generation. The agent reads the MCU (microcontroller unit = microcontrollore) and peripheral requirements from free text, fetches the correct STM32 package, generates the .ioc script, and runs STM32CubeMX in headless mode without GUI. A project that would take 20 minutes of clicking is done in 30 seconds.

The second workflow is AI Model Discovery and STEdgeAI Analysis. 
The system uses three paths to find a model: a curated task-based list of models, a custom URL the user provides, or an iterative web search on HuggingFace and GitHub. 
Once a model is selected, it goes through the STEdgeAI compiler, which checks its RAM and Flash footprint against the target MCU's limits. If it doesn't fit, it escalates the compression level on its own. 
If the model still exceeds the hardware constraints, the workflow stops and gives the user the choice between picking a lighter model or switching to a more capable board.

The third workflow is Firmware-AI Integration, which copies all AI files into the STM32 project tree and rewrites main.c to inject the inference call automatically. 
The result is a project ready to compile on-device.

The fourth workflow is Web Research. 
For technical questions, the agent queries DuckDuckGo, pulls page content from the RESULTS, and puts together a grounded answer (mette insieme una risposta fondata) scored automatically using DeepEval.


[Slide 4b - Customization workflow]
The fifth workflow is Neural Network Customization, the most technically involved part of the system. (la parte tecnicamente più coinvolta del sistema.)

The agent first inspects the model's architecture layer by layer, retrieves known best practices for that network family and then rewrites the Keras code directly: freezing backbone layers, replacing the classification head for a different number of output classes, injecting dropout. 
It also detects and fixes class mismatches automatically, before training starts. 
The user then chooses between a standard fine-tuning run and a full NNI hyperparameter search. 
In the second case, the system writes the trial script, the search space JSON, and the experiment config, then launches the NNI tuner (il cervello che sceglie quali iperparametri scegliere , il più comunque è il TPE) over learning rates and batch sizes. 
The best configuration is selected automatically and output is a validated model ready for STEdgeAI.

We also have Dataset and Synthetic data Workflows, which automatically fetch HuggingFace datasets OR generate synthetic VALIDATION SAMPLES for fast pipeline validation.

One key design detail is that outputs from each stage carry over automatically into the next (gli output di ogni fase vengono trasferiti automaticamente a quella successiva). For example, the MCU target set during firmware setup is already in context when the AI agent searches for a model. So we don't have repeated questions.

[Slide 5: IDE Integration & Human-in-the-Loop]
The assistant lives inside VS Code. Responses arrive token by token, and a progress bar updates at EACH NODE EXECUTION so the user knows exactly where the system is. 
At critical points the system pauses and asks for explicit confirmation in the chat, like right before a long training job or just before the STEdgeAI compiler runs.

Potential Q&A

Q1: Can you give a specific example of how the customization agent prevents errors?
A1: Say a user wants to deploy a model, but their dataset has 132 classes while the pre-trained model outputs 1000. Under normal conditions this class mismatch breaks the training script. Here, the agent reads the network architecture, spots the dimension conflict, and automatically rewrites the Keras code to fix the final output layer before training starts.

Q2: How do you guarantee that the generated C code is correct and actually compiles?
A2: The system does not generate C code from scratch. STEdgeAI handles the C code generation from the validated model file. The agent's role is to verify that the model's RAM and Flash footprint fit within the target board's physical constraints before handing off to the compiler. If the check fails, the agent intervenes before any code is generated.

Q3: Why Triton instead of keeping Ollama locally?
A3: During concurrent load testing with 15 users, individual Ollama instances caused VRAM saturation because each container locked its own GPU allocation. Triton runs a single shared pool and handles dynamic model swapping (if necessary), so GPU memory is never duplicated across users. At 15 concurrent sessions, VRAM stayed at 80% with full GPU utilization — well within the safe operating range of the A40.

Q4: What exactly does the integration agent write into main.c?
A4: STM32CubeMX generates main.c with reserved comment sections for user code. The agent targets those blocks precisely. In the includes section, it adds the generated network headers. In the private variables section, it declares the AI handle, the activation buffer, and the input/output data arrays. In the initialization block, it calls ai_network_create and ai_network_init with the correct parameters. Finally, in the main while loop, it inserts ai_network_run with inline comments explaining how to feed sensor data in and read the classification result. The source file is backed up before any modification.

Q5: How are two different users isolated on VS Code? What is the key that separates their sessions?
A5: Each request from the VS Code extension carries two identifiers: a user_id and a session_id. The server combines them into a composite key: composite_thread_id = f"{user_id}:{session_id}". This string becomes the LangGraph thread_id passed to the Redis checkpointer, so two users with different composite keys always operate on entirely separate MasterState snapshots, with no shared mutable state.

The user_id is currently hardcoded in the extension (set to "michele" during development). The session_id, on the other hand, is generated dynamically at extension activation using a timestamp:
  const SESSION_ID = `vscode-session-${Date.now()}`;
Because each VS Code window runs its own extension process and calls activate() independently, every new window gets a unique timestamp and therefore a unique SESSION_ID. This is what makes two windows behave as isolated users: same user_id, but different session_id, which results in a different composite thread key and a separate Redis checkpoint chain.

It is worth noting that this is session isolation, not authentication. 
In a possible future work like enterprise Kubernetes deployment, the extension would receive a per-user OAuth token at login time, making user_id unique and persistent across sessions rather than hardcoded.

Q6: If individual tasks show speedups of 40x and 30x, why is the end-to-end figure only 9x?
A6: The 9x is a weighted aggregate across all six pipeline stages, not just the most dramatic ones. The peak speedups — 40x for CubeMX project setup and 30x for NNI experiment generation — apply to pure orchestration tasks where we completely eliminate GUI interaction or manual script writing. The bottleneck is model fine-tuning, which still requires actual GPU compute time and shows only a 3x improvement: the agent handles setup and configuration automatically, but cannot compress the training epochs themselves. STEdgeAI analysis shows a 7x improvement for the same reason: CLI invocation is automated, but the compilation runtime remains. These two tasks represent roughly 75–90 minutes of the total manual baseline, so their lower speedup pulls the pipeline average down to 9x. This figure is consistent with what embedded ML CI/CD literature reports — typically 70% deployment time reduction through automation pipelines.

Q7: Does Redis only store user profiles, or does it do something more fundamental to the system?
A7: Redis serves two distinct roles. The first is as the LangGraph checkpointer: without a persistent backend, LangGraph falls back to an in-memory store that is lost the moment the HTTP response closes. In this system, when the graph hits a Human-in-the-Loop interrupt (for example before launching a fine-tuning job), the SSE connection closes and the user walks away. When they send the next message, a new HTTP request arrives — a completely separate connection. Redis is the only reason the orchestrator knows where it left off and can resume from that exact node, with the full MasterState intact. Without Redis, every message would restart the graph from zero. The second role is long-term user profiling: preferred board, last selected model, and previous project paths are persisted across sessions in a per-user Redis key, so the assistant remembers context between completely separate conversations.

Q8: Why does the system need a dedicated API Gateway layer? Could the LangGraph orchestrator expose its endpoint directly?
A8: Technically LangGraph does expose its own server, but introducing a dedicated FastAPI layer between the VS Code extension and the graph serves a concrete purpose. The FastAPI server handles all the HTTP protocol concerns that should not leak into the orchestration logic: it parses the incoming request, retrieves the user profile from Redis, constructs the initial MasterState, decides whether an incoming message is a new request or a resume from an interrupt, and translates all graph events into a structured NDJSON stream. If we let the extension talk directly to LangGraph's internal API, every change to the communication protocol or the streaming format would require touching the orchestration code. Keeping them separate means the graph only thinks in terms of state transitions, and the API layer only thinks in terms of HTTP.

Q9: How does the streaming work between the server and the VS Code extension? Why not a standard REST response?
A9: A standard REST response would block the extension UI until the entire graph execution completes, which can take several minutes for a fine-tuning job. Instead, the FastAPI server returns a StreamingResponse using Newline Delimited JSON (NDJSON): as soon as each graph node finishes, the server pushes a small JSON object over the already-open HTTP connection (a progress label, a markdown response chunk, or an interrupt prompt). The VS Code extension consumes these JSON lines incrementally and updates the chat panel in real time without waiting for the full response. A custom QueueHandler also intercepts Python log lines from training subprocesses (epoch counter, loss values) and injects them into the same NDJSON stream, so the user sees live training progress directly in the chat.

Q10: In the architecture slide, you mention the response is streamed "token by token". What exactly is a token in this context?
A10: A token is the fundamental unit of text that a Large Language Model processes. It is not necessarily a full word — depending on the tokenizer, a token can be a single character, a syllable, or a common word (on average, one token is about 3/4 of an English word). When I say the response is streamed "token by token", it means the LLM does not compute the entire paragraph in memory before sending it. It predicts the text sequentially, one token at a time. By streaming these tokens over the network as soon as the GPU computes them, the VS Code extension can create a real-time "typing" effect on the user's screen. This drastically improves the perceived latency, because the developer starts reading the answer immediately instead of waiting for the full generation to complete.

Q11: When the customization agent adapts MobileNetV1 for a 132-class dataset, what is actually happening under the hood?
A11: This is a classic transfer learning operation. MobileNetV1 is usually pre-trained on the ImageNet dataset, which has 1000 classes. This means its final classification layer (the "output head") has exactly 1000 neurons. If you try to train that raw model on a dataset with 132 classes (like Fruit-360), the training script will crash immediately due to a tensor shape mismatch. 
When the agent detects this conflict, it programmatically removes the original 1000-neuron dense layer from the Keras model. 
It then injects a new Dense layer with exactly 132 neurons (matching the new dataset), usually preceded by a Dropout layer to prevent overfitting. 
During the subsequent fine-tuning phase, the pre-trained "feature extractor" layers are often frozen, and only this new 132-neuron head is trained to map the extracted visual features to the new specific categories.

Q12: You mentioned Triton as your inference backend, but did you also use vLLM?
A12: Yes, but not as a separate service. vLLM runs as the internal runtime inside the Triton Python backend. When Triton loads the Mistral model, the model.py I wrote calls vllm.LLM() in its initialize() method to load the model weights onto the GPU, and llm.generate() in execute() for each inference request. The application code never speaks to vLLM directly: it only sees Triton's native API at /v2/models/mistral/infer. So Triton is the serving layer and vLLM is the inference engine underneath it — the two work together as a stack.

Q13: Why did you need vLLM inside Triton? Could you have used HuggingFace Transformers directly?
A13: Technically yes, but HuggingFace Transformers allocates the KV cache statically per request. With multiple concurrent users, each session reserves its own chunk of VRAM for the full context window, even if the actual prompt is short. vLLM solves this with PagedAttention, which manages the KV cache dynamically in fixed-size blocks — similar to how an operating system handles virtual memory pages. Unused blocks are released and reused across sessions. On top of that, vLLM implements continuous batching: it folds new incoming requests into the active generation batch without waiting for previous ones to finish, which keeps GPU utilization high under concurrent load.

Q14: What is the KV cache exactly?
A14: During text generation, Transformer models process every token in the sequence at every step. To avoid recomputing the Key and Value vectors for all previously generated tokens, the model saves them in memory — that is the KV cache. As generation continues, the cache grows linearly with the number of tokens produced. With many concurrent users, multiple independent KV caches accumulate in VRAM simultaneously. With static allocation (Transformers default), the full context window is reserved upfront regardless of actual length. PagedAttention in vLLM allocates only the pages that are actually needed, reclaiming memory as soon as a session ends.

Q15: You have gpu_memory_utilization=0.35 in model.py. Why such a conservative value?
A15: That parameter was calibrated during development on a local A4000 with 16GB of VRAM. Setting it to 0.35 reserved about 5.6GB for the Mistral 7B GPTQ-quantized weights, leaving the remaining 65% for the KV cache and peak activations during concurrent requests. On the HPP cluster with the A40 (45GB), the same 0.35 reserves around 15GB for weights, leaving roughly 30GB for KV cache and for coexisting with other heavy models like gpt-oss-20b without triggering a VRAM swap.
