Good afternoon everyone. I'm Michele Russo and today I present my thesis: "From IDE to Edge: A Cloud-Native Multi-Agent Framework for Automated Edge AI Deployment on STM32".

[Slide 2: The Core Problem]
Right now, a real disconnect exists in embedded development. AI engineers write Python and train large neural networks. Embedded engineers write C, fight strict memory limits and write low-level firmware directly on STM32 hardware.
Connecting those two worlds and pushing a neural network onto a microcontroller is called Edge AI. 
And right now, it is a highly manual process. Developers must master a fragmented toolchain, for example: STM32CubeMX for hardware configuration, STEdgeAI for model conversion, custom Python scripts for hyperparameter tuning, and manual C-code integration.
My tests show this pipeline takes an expert over 4 hours. Most of that time is wasted navigating dense GUIs, reading datasheets, writing repetitive code, and debugging tiny misconfigurations.
The answer I propose is to replace that tedious toolchain with a multi-agent AI framework and, instead of clicking through interfaces, the developer write a simple prompt to their IDE like: "Generate an STM32H7 project, find a small MobileNet and integrate it into my C code."

[Slide 3: Architecture — The Five Layers]
As shown in this diagram, the framework is organized across five distinct layers.

At the top is the IDE Layer. The developer interacts through a custom VS Code extension that integrates directly into the editor's native chat. By typing @stm32ai in the chat panel, they communicate with the backend container. Responses stream token by token, keeping the editor completely responsive even during long operations.

Below that is the API Gateway: a FastAPI server that exposes a single streaming endpoint. It receives each message from the extension, retrieves the user's long-term profile from Redis, constructs the initial graph state, and streams back real-time responses.

The core of the system is the Orchestration Layer. I built the entire pipeline using LangGraph. This framework lets you define workflows as directed, stateful graphs. In this topology, each node is a specialized Python function (such as invoking the STM32CubeMX CLI or running an STEdgeAI validation) and the LLM acts as the orchestrator, deciding which edges to follow based on the current context and the user's intent.

Then we have the State and Memory Layer. A dedicated Redis container serves two distinct roles. On one side, it is the LangGraph checkpointer: the full execution state is persisted at every node transition, enabling fault-tolerant resumption and Human-in-the-Loop pauses. On the other side, it stores per-user long-term profiles (preferred board, last model, previous project paths) that survive across sessions.

Finally, at the bottom is the Inference Layer. All LLM calls are forwarded over the network to a centralized NVIDIA Triton Inference Server on the lab's remote cluster. Triton handles dynamic model loading and shares GPU memory across concurrent users, so the orchestration containers need no GPU at all.

[Slide 4: LangGraph — The Seven Workflows]
Now let me go deeper into the Orchestration Layer.

When a new message arrives, an LLM-based router (running on Mistral via Triton) classifies the user's intent and dispatches it to one of the primary workflows. If the confidence score falls below 0.6, the system asks the user to pick from a menu explicitly, rather than guessing. Let me walk through all seven workflows.

The first workflow is Firmware Generation. The agent reads the MCU and peripheral requirements from free text, fetches the correct STM32 package, generates the .ioc script, and runs STM32CubeMX in headless mode with a virtual framebuffer. No GUI, no manual steps. A project that would take 20 minutes of clicking is done in 30 seconds.

The second workflow is AI Model Discovery and STEdgeAI Analysis. The system uses three paths to find a model: a curated task-based zoo, a custom URL the user provides, or an iterative web search on HuggingFace and GitHub. Once a model lands, it goes through the STEdgeAI compiler. The agent checks its RAM and Flash footprint against the target MCU's limits. If it doesn't fit, it escalates the compression level on its own. If the model still exceeds the hardware budget, the workflow stops and gives the developer a concrete choice: pick a lighter model or switch to a more capable board.

The third workflow is Firmware-AI Integration. After C code is generated, the developer can continue with integration. The agent scans the STEdgeAI output, copies the generated files into the STM32 project tree, and patches main.c to call the inference function. The result is a project ready to compile on-device.

The fourth workflow is Web Research. For technical questions, the agent classifies the search intent, queries DuckDuckGo, pulls the actual page content from the results, and puts together a grounded answer. Quality is scored automatically with DeepEval.

The fifth workflow is Neural Network Customization, the most technically involved part of the system. After download, the agent inspects the model's architecture node by node and retrieves known best practices for that network family. The user then says, in plain English, what they want changed. The agent rewrites the Keras code directly: freezing backbone layers, replacing the classification head for a different number of output classes, injecting dropout to counter overfitting. It also detects and fixes class mismatches automatically, before training starts. Once the user confirms the changes, they choose between a standard fine-tuning run and a full NNI hyperparameter search. In the second case, the system writes the trial script, the search space JSON, and the experiment config from scratch, then launches the NNI tuner over learning rates and batch sizes. The output is a validated model ready for the STEdgeAI stage.

The sixth workflow is Dataset Selection. The agent downloads a real dataset from HuggingFace or Kaggle, or registers a custom path the user provides.

The seventh workflow is Synthetic Data Generation. When no real dataset is available, or just for fast pipeline validation, the agent generates synthetic samples and checks their distribution before training begins.

One key design detail: outputs from each stage carry over automatically into the next. The MCU target set during firmware setup is already in context when the AI agent searches for a model. No repeated questions, no configuration drift between tools.

This framework shows that multi-agent orchestration is a practical path for embedded AI development. Headless CubeMX generation, a centralized Triton backend, and NNI optimization run together as a single system from inside the IDE.

The architecture is built for the next step. Because the orchestration containers carry no GPU dependency, moving to Kubernetes is a direct path: swap Docker Compose for a Kubernetes deployment and enterprise teams can scale the agent layer horizontally while Triton manages the GPU cluster.

Cutting a 4-hour pipeline to under 30 minutes is a concrete result. The system removes the expertise barrier that has kept embedded engineers and AI engineers working in separate silos.

Potential Q&A

Q1: Can you give a specific example of how the customization agent prevents errors?
A1: Say a user wants to deploy a model, but their dataset has 132 classes while the pre-trained model outputs 1000. Under normal conditions this class mismatch breaks the training script. Here, the agent reads the network architecture, spots the dimension conflict, and automatically rewrites the Keras code to fix the final output layer before training starts.

Q2: How do you guarantee that the generated C code is correct and actually compiles?
A2: The system does not generate C code from scratch. STEdgeAI handles the C code generation from the validated model file. The agent's role is to verify that the model's RAM and Flash footprint fit within the target board's physical constraints before handing off to the compiler. If the check fails, the agent intervenes before any code is generated.

Q3: Why Triton instead of keeping Ollama locally?
A3: During concurrent load testing with 15 users, individual Ollama instances caused VRAM saturation because each container locked its own GPU allocation. Triton runs a single shared pool and handles dynamic model swapping (if necessary), so GPU memory is never duplicated across users. At 15 concurrent sessions, VRAM stayed at 80% with full GPU utilization — well within the safe operating range of the A40.
