[Slide 1: Title & Introduction]
Good morning everyone. I'm Michele Russo and today I present my thesis: "From IDE to Edge: A Cloud-Native Multi-Agent Framework for Automated Edge AI Deployment on STM32".

[Slide 2: The Core Problem]
Right now, a real disconnect exists in embedded development. AI engineers write Python and train large neural networks. Embedded engineers write C, fight strict memory limits and write low-level firmware directly on STM32 hardware.
Connecting those two worlds and pushing a neural network onto a microcontroller is called Edge AI. 
And right now, it is a highly manual process. Developers must master a fragmented toolchain, for example: STM32CubeMX for hardware configuration, STEdgeAI for model conversion, custom Python scripts for hyperparameter tuning, and manual C-code integration.
My tests show this pipeline takes an expert over 4 hours. Most of that time is wasted navigating dense GUIs, reading datasheets, writing repetitive code, and debugging tiny misconfigurations.
The answer I propose is to replace that tedious toolchain with a multi-agent AI framework and, instead of clicking through interfaces, the developer write a simple prompt to their IDE like: "Generate an STM32H7 project, find a small MobileNet and integrate it into my C code."

[Slide 3: Architecture — The Five Layers]
(~2 minuti fin qui)

As shown in this diagram, the framework is structured across five distinct layers, each with a well-defined responsibility.

At the top is the IDE Layer. The developer interacts through a custom VS Code extension. It hosts a live chat panel directly inside the editor and streams responses asynchronously, so the editor stays responsive even during long operations.

Below that is the API Gateway. A FastAPI server exposes a single streaming endpoint. It receives each message from the extension, retrieves the user's long-term profile from Redis, constructs the initial graph state, and pipes back structured JSON events in real time.

The core of the system is the Orchestration Layer, and this is where I want to spend a moment. I built the entire agentic pipeline using LangGraph. LangGraph lets you define workflows as directed, stateful graphs, where each node is a specialist agent, and edges represent transitions between phases of the development lifecycle.

At the beginning, the master graph routes each user request to one of three primary workflows: Firmware Generation, AI Analysis, or Web Research. The AI workflow itself contains nested subgraphs for Model Customization and Firmware-AI Integration, which are reached through sequential inter-workflow transitions once the upstream stages are complete. Outputs from one stage automatically populate the inputs of the next, so the MCU target chosen during firmware setup is already in context when the AI agent starts looking for a compatible model. No repeated questions, no configuration mismatches.

Between workflows, LangGraph checkpoints the full state to Redis at every node transition. This means the system can resume from exactly where it left off after a Human-in-the-Loop pause, a network timeout, or any transient failure.

Below that is the State and Memory Layer. Redis serves two roles here: it is the LangGraph checkpointer, and it also stores per-user long-term profiles — preferred board, last model, previous project paths — that persist across sessions.

Finally, at the bottom is the Inference Layer. All LLM calls are forwarded over the network to a centralized NVIDIA Triton Inference Server, deployed on the inNuCE Lab cluster with an NVIDIA A40 and 45 GB of VRAM. Triton handles dynamic model loading and shares GPU memory across concurrent users. The local containers need no GPU at all.

[Slide 5: Diagram 1 — Firmware Generation & AI Model Discovery]
(~5 minuti fin qui)

Let me walk through the full pipeline using the three workflow diagrams from the thesis.

This first diagram shows what happens after the router makes its decision. If the user asks for a firmware project, the system collects the MCU and peripheral configuration in plain English, searches the STM32 package repository, generates the .ioc script, and runs the STM32CubeMX CLI in headless mode — no GUI, no manual steps. The project is ready in about 30 seconds.

If the user instead asks for an AI model, the system enters the model discovery branch. There are three paths: selecting a pre-validated model from the STM32 Model Zoo by task type, registering a custom model URL, or running an iterative web search on HuggingFace and GitHub. All three paths converge on a download step and then hand off to the next stage: model customization.

And at any point, if the user simply asks a technical question, the request exits immediately to the Web Research workflow — we will come back to that on the third diagram.

[Slide 6: Diagram 2 — Model Customization & NNI Optimization]
This second diagram covers the customization stage, which is the most technically complex part of the system.

After the model is downloaded, the agent inspects its architecture layer by layer. The user can then say, in plain English, what they want: freeze the backbone, inject a dropout, replace the output head for a custom number of classes. The agent rewrites the Keras code automatically.

Once the modifications are applied, the dataset is acquired — either a real dataset downloaded from HuggingFace or Kaggle, or synthetic data generated directly by the LLM for pipeline validation. Then comes the training decision. If the user asks for optimization, the system runs a full NNI experiment: trial script, search space, and experiment config are all generated from scratch, and the tuner searches over learning rates and batch sizes across multiple trials. Otherwise, a standard fine-tuning run executes with fixed hyperparameters. Either way, the final model is validated and saved.

[Slide 7: Diagram 3 — STEdgeAI Analysis, Integration & Web Research]
The third diagram covers the last three stages of the pipeline.

After training, the model goes through the STEdgeAI compiler. The agent checks its exact RAM and Flash footprint against the target board's physical limits. If it doesn't fit, the system escalates the compression level automatically. If it still exceeds the constraints, the workflow pauses and offers the developer two explicit choices: switch to a lighter model or swap the target hardware. Only when the model fits does the system proceed to C-code generation.

At that point, the developer is asked whether to integrate the generated code into the firmware project. If yes, the agent scans the X-CUBE-AI output files, copies them into the STM32 project directory, and patches main.c to wire in the inference call. The result is a project that is ready to compile.

On the right column of this same diagram is the Web Research workflow. When the user asks a technical question from the beginning of the system, the agent classifies the intent, queries DuckDuckGo, and synthesizes a grounded answer using the retrieved pages. Answer quality is measured automatically with DeepEval and shown to the user. After the search is done, the user can continue with another workflow or stop there.

Speed is meaningless without correctness. Two independent quality checks back the results.

On code quality: the customization agent successfully adapted a MobileNetV1 for a 132-class custom dataset, injecting a dropout and replacing the output head autonomously. The resulting model reached 98.1% validation accuracy on 5,000 images.

On knowledge quality: DeepEval measured an average Contextual Relevancy of 75% and a hallucination rate as low as 4% on procedural tasks, where the agent scored a perfect 1.0 on Faithfulness — meaning every factual claim traced back directly to a retrieved technical manual.

[Slide 11: Conclusion & Future Work]
(~12 minuti fin qui)

This framework shows that multi-agent orchestration is a viable path for embedded AI development. Headless CubeMX generation, a centralized Triton inference backend, and NNI optimization all run as a single, coherent system from inside the IDE.

The architecture is already designed for the next step. Because the orchestration containers are completely GPU-free, migrating to Kubernetes is straightforward — replacing Docker Compose with a Kubernetes deployment lets enterprise teams scale the agent layer horizontally while Triton continues to manage the GPU cluster.

Shrinking a 4-hour pipeline to under 30 minutes is a concrete result. The framework does not just automate steps — it removes the expertise barrier that currently keeps embedded engineers and AI engineers working in separate silos.

Potential Q&A

Q1: Can you give a specific example of how the customization agent prevents errors?
A1: Say a user wants to deploy a model, but their dataset has 132 classes while the pre-trained model outputs 1000. Under normal conditions this class mismatch breaks the training script. Here, the agent reads the network architecture, spots the dimension conflict, and automatically rewrites the Keras code to fix the final output layer before training starts.

Q2: How do you guarantee that the generated C code is correct and actually compiles?
A2: The system does not generate C code from scratch. STEdgeAI handles the C code generation from the validated model file. The agent's role is to verify that the model's RAM and Flash footprint fit within the target board's physical constraints before handing off to the compiler. If the check fails, the agent intervenes before any code is generated.

Q3: Why Triton instead of keeping Ollama locally?
A3: During concurrent load testing with 15 users, individual Ollama instances caused VRAM saturation because each container locked its own GPU allocation. Triton runs a single shared pool and handles dynamic model swapping (if necessary), so GPU memory is never duplicated across users. At 15 concurrent sessions, VRAM stayed at 80% with full GPU utilization — well within the safe operating range of the A40.
