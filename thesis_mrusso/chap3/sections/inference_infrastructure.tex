\section{The Inference Layer}
\label{sec:inference_infrastructure}

Every workflow node that requires natural-language reasoning delegates its request to a centralized inference abstraction. The utility function \texttt{get\_llm()} in \texttt{utils.py} serves as the single entry point: it receives a model name and optional parameters, then decides at runtime whether to route the request to a local Ollama instance or to a remote NVIDIA Triton Inference Server. This decision is based on a global \texttt{USE\_TRITON\_BACKEND} flag and the compatibility of the requested model with the Triton repository. The workflow code stays completely agnostic to the serving backend; changing engines requires toggling one flag and nothing else.

\subsection{Serving with Ollama}

The initial deployment relied on Ollama, an open-source tool that wraps quantized LLMs behind a local REST API. Each model is pulled once (\texttt{ollama pull mistral}) and served at \texttt{http://localhost:11434}. The LangGraph container communicated with it through the \texttt{ChatOllama} class from the \texttt{langchain-ollama} package.

Ollama worked well during early development. Its setup is minimal: one container, no custom configuration files, immediate model availability after the first download. During prototyping with limited resources, this simplicity is a clear advantage, since a developer with a single consumer GPU can run the entire pipeline locally without external dependencies.

The limitation appeared under multi-model and multi-user conditions. Ollama locks one GPU for one model at a time. Loading a second 7B model while the first is still resident causes VRAM exhaustion. In practice this forced sequential load/unload cycles (\texttt{keep\_alive=0}) that added latency and occasionally triggered process crashes when the unload did not complete before the next load request arrived.

\subsection{Serving with NVIDIA Triton Inference Server}

To overcome these concurrency constraints, I migrated the inference backend to NVIDIA Triton Inference Server. Triton manages a \textit{model repository}: a directory tree where each subfolder contains a model configuration (\texttt{config.pbtxt}) and the corresponding backend (Python, ONNX, TensorRT, or vLLM). The server exposes both HTTP and gRPC endpoints and handles model lifecycle, batching, and scheduling internally.

\subsubsection{Custom LangChain Integration: \texttt{ChatTriton}}

LangGraph expects LLM providers that implement the LangChain \texttt{BaseChatModel} interface. Triton has no native LangChain adapter, so I wrote a custom wrapper class, \texttt{ChatTriton} (in \texttt{triton\_client.py}), that converts LangChain message lists into the prompt format expected by the Triton Python backend, sends the inference request via the native V2 HTTP API (\texttt{POST /v2/models/\{model\}/infer}), and parses the response back into a LangChain \texttt{AIMessage}.

The same file provides \texttt{TritonEmbeddings}, a lightweight embedding client that routes \texttt{embed\_documents()} and \texttt{embed\_query()} calls to a \texttt{nomic-embed} model configured to run on CPU, so it does not compete for GPU memory with the heavier LLMs.

\subsubsection{Explicit Model Control and Dynamic Swapping}

Triton is launched with the \texttt{--model-control-mode=explicit} flag. In this mode no model is loaded at startup. The \texttt{ChatTriton} client manages the full lifecycle through a three-stage strategy implemented in its \texttt{\_ensure\_model\_loaded()} method.

First, it performs a \textit{fast-path check}: a query to the Triton repository index reveals whether the target model is already in \texttt{READY} state. If so, inference proceeds immediately. Second, if the model is not loaded, the client issues an \textit{optimistic load} via \texttt{POST /v2/repository/models/\{model\}/load}. When enough VRAM is available, this call succeeds without disrupting other loaded models. Third, if Triton rejects the load request (HTTP 400, typically due to GPU memory exhaustion), an \textit{OOM fallback} activates: the client iterates over all other registered LLMs, unloads them one by one through the \texttt{/unload} endpoint, waits for their status to transition to \texttt{UNAVAILABLE}, and retries the load.

After a successful load, the client polls the V2 infer endpoint with a lightweight probe request until the backend is fully operational. This extra step is needed because the Python backend's internal CUDA context initialization can lag behind the repository status flip.

The net effect is that only one large language model occupies VRAM at any given time, while the mechanism stays invisible to the workflow nodes.

\subsection{GPU Memory Management for Concurrent Workloads}

When inference and training share the same GPU, explicit VRAM partitioning becomes necessary. TensorFlow defaults to allocating all available GPU memory at initialization. If multiple users trigger model inspection or fine-tuning concurrently, the first subprocess monopolizes the device and subsequent sessions crash with Out-of-Memory exceptions.

To support concurrent access, the framework injects strict virtual device configurations before executing any Keras or TensorFlow operation:

\begin{lstlisting}[language=Python, caption={Strict VRAM partitioning for concurrent TensorFlow subprocesses}, label={lst:vram_partitioning}]
# Prevent greedy VRAM allocation by forcing a hard limit
gpus = tf.config.list_physical_devices('GPU')
if gpus:
    for gpu in gpus:
        tf.config.experimental.set_virtual_device_configuration(
            gpu,
            [tf.config.experimental.VirtualDeviceConfiguration(memory_limit=4096)]
        )
\end{lstlisting}

This caps fine-tuning tasks at 4~GB and lightweight model inspection at 1~GB. On a standard research GPU the configuration supports three to four simultaneous fine-tuning sessions or up to fifteen concurrent inspection calls. The orchestrator also provides utility functions (\texttt{force\_unload\_triton()}, \texttt{reload\_triton\_models()}) that release LLM VRAM before launching a training subprocess and reload the models once training completes.
