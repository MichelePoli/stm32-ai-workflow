\section{System Architecture}
\label{sec:architecture}

The implemented framework follows a modular, graph-based architecture where autonomous agents orchestrate the entire MLOps pipeline through a stateful execution model. Unlike traditional linear scripts, the system utilizes \textbf{LangGraph} to define workflows as directed graphs with conditional routing, enabling complex multi-step processes with human oversight at decision points.

\subsection{Containerized Deployment and GPU Decoupling}
To ensure scalability and efficient resource management in a multi-user environment, the entire architecture is containerized using Docker. A major architectural shift from early development was the transition from local per-container inference engines (such as Ollama) to a centralized \textbf{NVIDIA Triton Inference Server}. 

Running individual Ollama instances required locking a specific GPU for a single user throughout their session, preventing resource sharing. By decoupling the multi-agent pipeline from the inference engine, the user's LangGraph container requires only CPU and RAM. The Triton server acts as a centralized backend that receives requests via standardized APIs (compatible with the OpenAI format) and manages the GPU dynamically. This allows multiple LangChain instances to share resources simultaneously, drastically improving system scalability for future cluster deployments.

\subsection{Master Orchestrator and State Machine}

The core orchestration logic resides in \texttt{graph.py}, which implements a \textbf{Master StateGraph} that routes user requests to specialized subgraphs based on intent classification. The system operates through a centralized state object (\texttt{MasterState}) that persists across all workflow nodes, ensuring coherence and traceability throughout the execution.

\subsubsection{Four-Branch Workflow Architecture}

User requests are classified into four primary workflow categories:

\begin{enumerate}
    \item \textbf{Firmware Generation} (\texttt{firmware\_flow}): Automates STM32CubeMX project initialization, package installation, and code generation via CLI scripting.

    \item \textbf{AI Model Discovery and Optimization} (\texttt{ai\_flow}): Implements a two-tier model discovery system (curated task-based models + iterative web search), followed by neural network customization and hyperparameter optimization with NNI.

    \item \textbf{Firmware-AI Integration} (\texttt{integration\_flow}): Merges generated C inference code into the STM32 project structure and verifies build compatibility.

    \item \textbf{Web Research} (\texttt{search\_flow}): Provides technical guidance through RAG-enhanced web search with quality evaluation metrics.
\end{enumerate}

The routing decision is performed by an LLM-based classifier that analyzes the user's natural language input and returns a structured decision object:

\begin{lstlisting}[language=Python, caption={LLM-based routing logic from graph.py}, label={lst:routing}]
# From src/assistant/graph.py - route_request()
llm_router = ChatTriton(model="mistral").with_structured_output(RouteDecision)

result = llm_router.invoke([
    SystemMessage(content=router_instructions),
    HumanMessage(content=f"Request: {state.message}")
])

state.route = result.route  # "firmware", "ai_analysis", "integration", or "web_research"

if result.confidence < 0.6:
    logger.warning(f"Low confidence ({result.confidence:.2f}), requesting clarification")
    state.route = "unknown"
\end{lstlisting}

If the classifier's confidence falls below 0.6, the system enters a clarification loop where the user is prompted to explicitly select the desired workflow from a structured menu.

\subsubsection{State Management and Persistence}

All workflow data is stored in a single \texttt{MasterState} object defined in \texttt{state.py}. This Pydantic-based state class contains over 50 typed attributes covering:

\begin{itemize}
    \item \textbf{User Input}: Original message, intent classification, routing metadata
    \item \textbf{Firmware Workflow}: Board name, MCU series, .ioc file path, CubeMX output directory
    \item \textbf{AI Workflow}: Model path, task type, target MCU, compression level, search iteration count
    \item \textbf{Customization}: Model layers, modification parameters, NNI experiment directory
    \item \textbf{Integration}: Generated code paths, build status
    \item \textbf{Web Research}: Query history, search results, evaluation scores
\end{itemize}

This persistent state model enables \textbf{Context Chaining}, a key architectural feature where outputs from upstream workflows (e.g., the specific MCU target selected during \texttt{firmware\_flow}) automatically populate the input context for downstream workflows (\texttt{ai\_flow}). This eliminates redundant user data entry and prevents configuration mismatches, such as selecting an AI model incompatible with the previously generated firmware board. The state object acts as a \textit{single source of truth}, synchronizing project parameters across heterogeneous toolchains (CubeMX, STEdgeAI, TensorFlow).

LangGraph automatically persists this state at every node transition through a checkpointing mechanism, enabling:

\begin{enumerate}
    \item \textbf{Fault Tolerance}: Resume execution from the last successful checkpoint after transient failures
    \item \textbf{Human-in-the-Loop Gates}: Suspend execution for user approval without losing context
    \item \textbf{Time-Travel Debugging}: Replay past executions to diagnose workflow errors
\end{enumerate}

The state persistence layer is implemented using \textbf{Redis}, a high-performance in-memory data store, chosen for its low latency and native support for asynchronous operations. The framework adopts a \textbf{Dual-Layer Memory Architecture}:

\begin{enumerate}
    \item \textbf{Short-Term Memory (Session State)}: Managed by LangGraph's checkpointer, this layer stores the transient state of the active workflow graph. It is keyed by a composite \texttt{thread\_id} (user\_id + session\_id) and allows for granular time-travel debugging and fault tolerance within a single conversation.

    \item \textbf{Long-Term Memory (User Profile)}: A separate persistent store keyed by \texttt{user\_id}. This layer survives across sessions and retains critical context such as the user's preferred hardware board (\texttt{last\_board}), code generation style, and past project paths. This enables "Context Chaining" not just within a workflow, but across the entire lifecycle of the user's interaction with the system.
\end{enumerate}

The state is serialized as JSON and stored asynchronously in Redis, decoupling the persistence overhead from the real-time execution loop.

\subsubsection{System Integrity and Transactional Registration}

To maintain the stability of the model registry, the framework implements a \textbf{Transactional Registration Flow} for user-provided models. When a user submits a new model URL, the entry is first held in a \textit{Pending} state within the \texttt{MasterState}. The system then performs an autonomous validation via the STEdgeAI analysis engine. Only upon successful technical profiling (\texttt{analyze\_success = true}) is the model permanently committed to the \texttt{predefined\_models.json} registry. This transactional behavior ensures that the system's knowledge base remains free from broken links, malformed architectures, or incompatible file formats.

\subsection{Configuration Management}

Runtime parameters are managed through a dedicated \texttt{Configuration} class (\texttt{configuration.py}) that loads settings from:

\begin{itemize}
    \item \textbf{Environment Variables}: ST credentials (\texttt{ST\_EMAIL}, \texttt{ST\_PASSWORD}), API keys
    \item \textbf{Config File}: \texttt{config.json} for paths (CubeMX binary, STM32Cube repository, AI output directories)
    \item \textbf{LangGraph Runtime Config}: Passed via \texttt{config} parameter to each node
\end{itemize}

Critical configuration parameters include:

\begin{itemize}
    \item \texttt{local\_llm}: Language model ID (default: \texttt{mistral:latest})
    \item \texttt{llm\_temperature}: Sampling temperature (0.0 for deterministic routing, 0.2 for code generation)
    \item \texttt{llm\_context\_window}: Token limit (4096–8192 depending on task complexity)
    \item \texttt{cubemx\_path}: Absolute path to STM32CubeMX CLI executable
    \item \texttt{ai\_target}: Target MCU for STEdgeAI tooling (e.g., \texttt{stm32h743})
    \item \texttt{ai\_compression}: Quantization level (\texttt{low}, \texttt{medium}, \texttt{high}, \texttt{very\_high})
\end{itemize}

The configuration is validated at runtime using Pydantic validators, ensuring all required paths exist and credentials are correctly formatted before workflow execution begins.

\subsection{Graph Topology and Node Composition}

Each of the four primary workflows is implemented as a \textbf{subgraph} with its own internal routing logic. The master graph connects these subgraphs through conditional edges that allow \textit{inter-workflow transitions} based on user decisions:

\begin{itemize}
    \item After completing firmware generation, the system offers to proceed to AI model discovery
    \item After AI model optimization, the system offers to integrate the generated C code into the firmware project
    \item At any point, users can invoke web research to gather technical documentation
\end{itemize}

This multi-stage pipeline mirrors the typical embedded AI development lifecycle:

\begin{center}
    \texttt{Hardware Setup → Model Selection → Model Customization → Code Generation → Integration → Testing}
\end{center}

The graph construction logic resides in four builder functions:

\begin{itemize}
    \item \texttt{build\_firmware\_graph()}: Firmware workflow (Workflow 1)
    \item \texttt{build\_ai\_analysis\_graph()}: AI discovery + customization (Workflows 2, 5, 6, 7)
    \item \texttt{build\_integration\_graph()}: Firmware-AI integration (Workflow 3)
    \item \texttt{build\_web\_search\_graph()}: Web research (Workflow 4)
\end{itemize}

Each builder function assembles nodes, defines conditional edges, and sets up interrupt points for human approval.

\subsection{Logging and Observability}

The system implements structured logging across all workflow nodes with severity levels:

\begin{itemize}
    \item \texttt{DEBUG}: Detailed execution traces (LLM prompts, API responses, state transitions)
    \item \texttt{INFO}: High-level progress indicators (workflow entry, node completion)
    \item \texttt{WARNING}: Non-fatal issues (low LLM confidence, fallback activations)
    \item \texttt{ERROR}: Recoverable failures (API timeouts, invalid user input)
\end{itemize}

Log entries include contextual metadata such as workflow name, current node, and relevant state variables, enabling rapid debugging of complex multi-step executions.

Additionally, the framework emits progress updates to the LangGraph API server, which can be consumed by frontend clients (e.g., Gradio UI, REST API consumers) for real-time status visualization.

\subsection{Interactive IDE Integration: VS Code Extension}

To connect the MLOps orchestration with the developer's daily workflow, a custom \textbf{Visual Studio Code Extension} acts as the primary interface for the assistant. This integration transforms the framework from a disconnected backend service into a real-time, context-aware companion embedded directly within the Integrated Development Environment (IDE), completely eliminating previous dependencies on external interfaces like LangSmith.

\subsubsection{Client-Server Communication via FastAPI}

The extension communicates with the LangGraph orchestrator through a lightweight \textbf{FastAPI backend} (\texttt{server.py}). This architectural choice provides several benefits:
\begin{itemize}
    \item \textbf{Asynchronous Event Streaming}: The server uses an \texttt{event\_generator} function that leverages Python's \texttt{asyncio} to stream graph events to the client in real-time. Each node execution in the graph triggers a JSON event containing progress updates, partial markdown responses, or routing decisions.
    \item \textbf{Decoupled Execution}: The complex neural network computations and toolchain invocations run in a dedicated Python process, preventing the VS Code frontend from freezing during intensive tasks.
    \item \textbf{API-Driven Extensibility}: The same backend can simultaneously serve multiple clients (CLI, Web UI, IDE), ensuring a consistent project state across different views.
\end{itemize}

\subsubsection{VS Code Chat Participant API}

The frontend is implemented using the \textbf{VS Code Chat Participant API}, which allows the assistant to participate in the native GitHub Copilot-style chat interface. The extension handles the following event stream logic:
\begin{itemize}
    \item \textbf{Progress Reporting}: Server-emitted \texttt{progress} events are rendered as real-time bullet points (e.g., \textit{"Routing to AI Flow..."}, \textit{"Downloading MobileNetV2..."}), providing the user with visibility into the assistant's internal reasoning steps.
    \item \textbf{Markdown Rendering}: Final reports and intermediate task lists are streamed as Markdown, allowing for rich formatting, code blocks, and clickable file links.
    \item \textbf{Cancellation Handling}: The extension propagates VS Code cancellation tokens to the Python server, allowing the backend to gracefully interrupt long-running LangGraph executions if the user closes the chat session.
\end{itemize}

By embedding the assistant within the IDE, the framework gains access to the local file system context, enabling features like automatic path resolution for \texttt{.ioc} files and direct opening of generated C source code upon completion of the integration workflow.
