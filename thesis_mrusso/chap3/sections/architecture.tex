\section{Introduction and System Architecture Overview}
\label{sec:architecture}

The framework is organized as a multi-layered, cloud-native stack that connects the developer's local IDE to a centralized GPU cluster on the other end of the chain. As shown in Figure~\ref{fig:top_down_architecture}, five distinct layers handle different concerns: user interaction, request routing, agentic orchestration, state persistence, and language model inference.

\input{chap3/sections/system_architecture_diagram.tex}

Each layer has a well-defined responsibility and communicates with the adjacent ones through standardized interfaces:

\begin{enumerate}
    \item \textbf{IDE Layer.} The developer interacts with the system through a custom \textbf{VS Code} extension that hosts the chat interface directly inside the editor. Responses are streamed asynchronously over an NDJSON connection, so the editor stays responsive even during long-running tasks such as model training or firmware compilation.

    \item \textbf{API Gateway Layer.} A \textbf{FastAPI} server, running in the \texttt{langgraph-app} container, exposes a single \texttt{/stream} endpoint. It receives user messages from the extension, retrieves the user's long-term profile from \textbf{Redis}, constructs the initial graph state, and streams back structured JSON events as the graph executes. Although it shares the same container as the orchestration engine, it encapsulates a distinct concern: protocol translation between the HTTP world and the graph execution model.

    \item \textbf{Orchestration Layer.} A \textbf{LangGraph} stateful graph coordinates the entire agentic pipeline. An LLM-based router classifies each incoming request and dispatches it to one of three primary subgraphs (firmware, AI analysis, or web research), while the remaining workflows are reached through inter-workflow transitions. Domain-specific tools, namely \textbf{STM32CubeMX}, \textbf{STEdgeAI}, and \textbf{Microsoft NNI}, run as managed subprocesses inside the same container, invoked by the agent nodes and wrapped to normalize their CLI output into structured state updates.

    \item \textbf{State \& Memory Layer.} A dedicated \textbf{Redis} container serves two distinct roles. First, it acts as the LangGraph checkpointer, persisting the full \texttt{MasterState} at every node transition to support fault-tolerant resumption and Human-in-the-Loop (HITL) interrupts. Second, it stores per-user long-term profiles (preferred board, last model, project paths) that survive across sessions.

    \item \textbf{Inference Layer.} All LLM calls are forwarded over the network to a centralized \textbf{NVIDIA Triton Inference Server} deployed on the inNuCE Lab Heterogeneous Prototyping Platform (HPP) \cite{innuce_website}, which mounts an NVIDIA A40 with 45~GB of VRAM. Triton handles dynamic model loading and GPU memory sharing across concurrent users, keeping the local orchestration containers free of any GPU dependency.
\end{enumerate}

The \textbf{Orchestration Layer} (L3) coordinates five agentic workflows, each mapping to a specific phase of the Edge AI development lifecycle:

\begin{enumerate}
    \item \textbf{Firmware Generation} (\texttt{firmware\_flow}): Automates STM32CubeMX project initialization, package installation, and code generation via CLI scripting.
    \item \textbf{AI Model Discovery and Optimization} (\texttt{ai\_flow}): Implements a two-tier model discovery system (curated task-based models plus iterative web search), followed by STEdgeAI analysis, validation, and C code generation.
    \item \textbf{Model Customization} (\texttt{customization\_flow}): Enables layer-level neural network modification, dataset handling, and automated hyperparameter optimization with NNI.
    \item \textbf{Firmware-AI Integration} (\texttt{integration\_flow}): Merges generated C inference code into the STM32 project structure and verifies build compatibility.
    \item \textbf{Web Research} (\texttt{search\_flow}): Provides technical guidance through dynamic web search with DeepEval quality evaluation metrics.
\end{enumerate}

When a new message arrives, the orchestrator routes it through an LLM-based classifier. The classifier analyzes the user's natural language input, assigns a confidence score, and selects the target workflow. If confidence falls below $0.6$, the system asks the user to choose explicitly from a structured menu. Figure~\ref{fig:routing_flowchart} illustrates this decision process.
