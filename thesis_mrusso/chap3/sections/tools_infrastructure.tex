\section{Tooling Infrastructure}
\label{sec:tools}

The framework combines several specialized open-source tools to cover inference, web search, quality evaluation, vector storage, and neural network deployment.

\subsection{DuckDuckGo Search Integration}

Workflow 4 uses the \texttt{duckduckgo-search} (\url{https://pypi.org/project/duckduckgo-search/}) Python library to execute web queries. Early prototypes relied on agentic frameworks like Agno, which required LLM-specific function calling to extract parameters and invoke the search engine. 

To ensure compatibility with the centralized Triton Inference Server (which proxies raw token streams and lacks native support for complex tool-calling schemas), we transitioned to a decoupled approach. The LangGraph orchestrator now extracts search queries via structured output prompts. It then executes the search directly using the Python library, bypassing the LLM's function-calling layer entirely.

\subsection{DeepEval for RAG Quality Assessment}

DeepEval (\url{https://github.com/confident-ai/deepeval}) implements the LLM-as-a-Judge paradigm for automated output evaluation. After Workflow 4 generates a summary, four metrics are computed against the retrieved documents:

\begin{enumerate}
    \item \textbf{Faithfulness}: $\frac{\text{Grounded Claims}}{\text{Total Claims}}$
    \item \textbf{Answer Relevancy}: $\frac{\text{Relevant Statements}}{\text{Total Statements}}$
    \item \textbf{Contextual Relevancy}: $\frac{\text{Useful Retrieved Docs}}{\text{Total Retrieved Docs}}$
    \item \textbf{Hallucination}: $1 - \frac{\text{Contradicted/Unsupported Claims}}{\text{Total Claims}}$
\end{enumerate}

All four metrics were initially evaluated by a local \texttt{OllamaModel} backed by \texttt{deepseek-r1:latest}, keeping the evaluation pipeline fully offline. Following the architectural migration to the HPP cluster (detailed in Section~\ref{sec:scalability_scenarios}), the evaluation was also performed using \texttt{gpt-oss-20b} served via the \textbf{NVIDIA Triton Inference Server}. The threshold for all metrics is set to 0.55. Evaluation runs synchronously in a separate thread via \texttt{asyncio.to\_thread} to avoid blocking the main event loop.

\subsection{Ollama: Local Development and Benchmarking}

During the initial development phase, \textbf{Ollama} (\url{https://ollama.com}) served as the primary inference backend for evaluating candidate models locally. Three practical advantages drove this choice: it kept all processing on-device (no sensitive source code or proprietary datasets left the machine), it eliminated network latency from the inference path, and it allowed unrestricted daily experimentation without per-token costs.

The benchmarking results from this phase, summarized in Section~\ref{sec:llm_selection}, informed the final model selection for the production Triton deployment.

\subsection{NVIDIA Triton Inference Server}

In the production architecture, \textbf{NVIDIA Triton Inference Server} is the primary inference backend. Centralizing model execution resolves a practical constraint encountered during development: per-user Docker containers with embedded Ollama bind a dedicated GPU for the entire duration of each session, preventing concurrent access. Triton replaces those isolated instances with a single shared server that handles all model requests through a unified queue.

\subsubsection{Model Repository Structure}

Triton reads models from a structured directory tree where each subdirectory corresponds to one deployed model. Each model entry contains a Protocol Buffer configuration file (\texttt{config.pbtxt}) and a versioned implementation directory:

\begin{verbatim}
model_repository/
+-- mistral/
|   +-- config.pbtxt
|   \-- 1/
|       \-- model.py
+-- deepseek-r1/
|   +-- config.pbtxt
|   \-- 1/
|       \-- model.py
\-- gpt-oss-20b/
    +-- config.pbtxt
    \-- 1/
        \-- model.py
\end{verbatim}

The \texttt{config.pbtxt} file defines the model's I/O contract, the serving backend, and the GPU allocation policy. For the Mistral entry:

\begin{verbatim}
name: "mistral"
backend: "python"
max_batch_size: 1

input  [{ name: "PROMPT",   data_type: TYPE_STRING, dims: [1] }]
output [{ name: "RESPONSE", data_type: TYPE_STRING, dims: [1] }]

instance_group [{ kind: KIND_GPU, count: 1 }]
\end{verbatim}

\subsubsection{EXPLICIT Model Control and Model Swapping}

Triton is configured with \texttt{model\_\allowbreak control\_\allowbreak mode: EXPLICIT}, disabling automatic model loading at boot time. Each model loads into VRAM on demand and unloads via API when no longer needed. We added this feature specifically for constrained hardware, such as a single 16~GB GPU, where keeping multiple 7B--20B models resident simultaneously would cause immediate memory failure.

The \texttt{ChatTriton} client class implements a \textbf{mutual exclusion swapping} algorithm in its \texttt{\_\allowbreak ensure\_\allowbreak model\_\allowbreak loaded()} method. Before loading the requested model, the method calls Triton's \texttt{/v2/repository/models/\{name\}/unload} endpoint for every other active LLM. It then polls \texttt{/v2/repository/index} until each reaches the \texttt{UNAVAILABLE} state. A two-second sleep after each unload gives the Python backend time to release its CUDA context before the next load begins. This guarantees only one heavyweight LLM resides in VRAM at any point to prevent Out-Of-Memory errors.

If the requested model is already in the \texttt{READY} state, the method returns immediately without unloading, minimizing VRAM churn. This is the standard behavior in the target HPP deployment: the 40~GB GPU capacity easily allows both Mistral and \texttt{gpt-oss-20b} to remain resident. Once the target model reports \texttt{READY} in the repository index, a lightweight probe checks the native inference endpoint (\texttt{/v2/models/\{name\}/infer}) to confirm it is live before forwarding the request.

This architectural design solves the bottlenecks of Ollama's single-process model. Ollama lacks an equivalent model lifecycle API. It loads one model at a time and exposes no mechanism to explicitly unload a model or queue a pending request. Under concurrent multi-model workloads lacking sufficient VRAM, Ollama simply crashes under constant churn. The Triton client's explicit swap logic fixes this flaw, guaranteeing high availability on constrained local nodes while scaling seamlessly up to the robust HPP hardware.


\subsubsection{vLLM and PagedAttention}

Memory efficiency within each model's active session is handled by \textbf{vLLM}, integrated as the Python backend behind Triton. vLLM implements \textbf{PagedAttention}, which manages the transformer KV cache as small non-contiguous physical pages rather than one large pre-allocated contiguous block. This reduces fragmentation and allows the system to accommodate longer effective context windows without reallocating VRAM between requests.


\subsection{STEdgeAI CLI}

STMicroelectronics' official toolchain for neural network deployment to X-CUBE-AI:

\begin{verbatim}
stedgeai analyze --model <model.h5> --target <stm32h743>
stedgeai validate --model <model.h5> --target <stm32h743>
stedgeai generate --model <model.h5> --compression <high>
\end{verbatim}

The toolchain converts Keras or TFLite models into optimized C code compatible with the X-CUBE-AI runtime library (v9.x). The three commands are called in sequence by Workflow 2: \texttt{analyze} profiles resource usage, \texttt{validate} confirms operator support on the target MCU, and \texttt{generate} produces the final inference artifacts.

\subsection{NNI: Neural Network Intelligence}

Microsoft's NNI framework (\url{https://nni.readthedocs.io}) handles hyperparameter search in Workflow 5. Rather than using NNI's static YAML configuration files, the framework generates experiment code programmatically at runtime. This lets the search space be constructed dynamically from the actual Keras model architecture under optimization, with custom trial logic for memory footprint control and adaptive layer replacement embedded directly in the generated scripts. Best-trial extraction and retraining are also triggered programmatically at the end of each experiment.

Supported tuners include TPE (Tree-structured Parzen Estimator), Random Search, Grid Search, and SMAC.
