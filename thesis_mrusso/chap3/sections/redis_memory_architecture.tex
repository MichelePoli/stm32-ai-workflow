\section{Redis Dual-Memory Architecture}
\label{sec:redis_architecture}

The framework utilizes a dual-layer memory system built on Redis, providing both transient workflow state persistence and long-term user context retention. This architecture is necessary for supporting Human-in-the-Loop workflows and multi-session context chaining.

\subsection{Architectural Overview}

Unlike traditional stateless APIs, the framework maintains two levels of memory:

\begin{enumerate}
  \item \textbf{Short-Term Memory (Session State)}: Managed by LangGraph's checkpointing system via \texttt{AsyncRedisSaver}. Stores the transient state of the active workflow graph, enabling fault tolerance and HITL interrupt/resume.
  \item \textbf{Long-Term Memory (User Profile)}: A custom persistent storage layer keyed by \texttt{user\_id}. Survives across sessions and retains context such as preferred hardware boards, code generation style, and past project paths.
\end{enumerate}

This dual-layer design enables \textbf{Context Chaining}, where outputs from previous sessions (e.g., the specific MCU target selected during \texttt{firmware\_flow}) automatically pre-populate input context for future workflows (e.g., \texttt{ai\_flow}), eliminating redundant user data entry.

\subsection{Redis Key Structure Design}

The framework uses a hierarchical key naming convention to organize data in Redis, ensuring clear separation between transient checkpoints and persistent profiles.

\subsubsection{Short-Term Memory (LangGraph Checkpoints)}

LangGraph checkpoints are stored using a composite key structure:
\begin{verbatim}
checkpoint:{user_id}:{session_id}:{checkpoint_id}
\end{verbatim}

The key is composed of three primary elements: the \texttt{user\_id} (e.g., ``michele''), which serves as the unique identifier for the user; the \texttt{session\_id} (e.g., ``vscode-session''), which identifies the specific interface or session instance; and the \texttt{checkpoint\_id}, a timestamp-based unique ID managed automatically by LangGraph for each state snapshot.

\textbf{Example Keys:}
\begin{verbatim}
checkpoint:michele:vscode-session:1707575432123
checkpoint:michele:vscode-session:1707575455789
checkpoint:john:cli-session:1707575500000
\end{verbatim}


This hierarchical organization ensures strict User Isolation, preventining different users from sharing or accessing each other's checkpoints. Furthermore, it supports Session Multiplexing, allowing a single user to run multiple independent workflows simultaneously across different clients like VS Code and CLI. Since checkpoint IDs are timestamped, the system also maintains a clear temporal ordering, which enables critical features like time-travel debugging.

\subsubsection{Long-Term Memory (User Profiles)}

User profiles follow a simpler key structure for direct access:
\begin{verbatim}
user:{user_id}:profile
\end{verbatim}
Example keys for this layer include \texttt{user:michele:profile} and \texttt{user:john:profile}.

\textbf{Profile Schema:}
The profile value is a JSON-serialized dictionary containing persistent user preferences:

\begin{lstlisting}[language=json, caption={User profile schema stored in Redis}, label={lst:profile_schema}]
{
  "board_name": "NUCLEO-H743ZI",
  "mcu_series": "STM32H7",
  "last_model": "mobilenet_v1_0.25_128",
  "last_project_path": "/home/user/workspace/h7_project",
  "last_workflow": "firmware",
  "timestamp": "2024-02-10T14:35:22Z"
}
\end{lstlisting}

\textbf{Profile Fields:}
\begin{itemize}
  \item \texttt{board\_name}: The most recently used STM32 board (e.g., ``NUCLEO-H743ZI''), used to pre-fill firmware generation requests
  \item \texttt{mcu\_series}: The series of the target MCU (e.g., ``STM32H7'')
  \item \texttt{last\_model}: The last AI model selected for optimization or integration
  \item \texttt{last\_project\_path}: Path of the most recently generated or targeted firmware project directory
  \item \texttt{last\_workflow}: The last executed workflow route (e.g., ``firmware'', ``ai\_analysis'')
  \item \texttt{timestamp}: Timestamp of the last successful workflow completion
\end{itemize}

\subsection{LangGraph Integration: \texttt{AsyncRedisSaver}}

The short-term memory layer is implemented using LangGraph's \texttt{AsyncRedisSaver} class, which abstracts Redis I/O operations.

\subsubsection{Initialization (\texttt{server.py})}

The checkpointer is initialized during FastAPI server startup:

\begin{lstlisting}[language=Python, caption={Redis checkpointer initialization in server.py}, label={lst:redis_init}]
from langgraph.checkpoint.redis.aio import AsyncRedisSaver
import redis.asyncio as redis

# 1. Create async Redis client
checkpointer_redis = redis.from_url(
    "redis://localhost:6379/0",
    encoding="utf-8",
    decode_responses=True
)

# 2. Initialize AsyncRedisSaver
memory = AsyncRedisSaver(redis_client=checkpointer_redis)

# 3. Setup internal RedisVL indexes (run once on startup)
await memory.setup()

# 4. Compile graph with checkpointer
graph = builder.compile(checkpointer=memory)
\end{lstlisting}

The \texttt{memory.setup()} call creates internal Redis indexes used by RedisVL for efficient checkpoint retrieval and time-travel queries.

\subsubsection{Checkpoint Serialization}

Each time a graph node completes execution, LangGraph automatically persists the \texttt{MasterState} to Redis. The checkpoint payload is a MessagePack or JSON-serialized structure:

\begin{verbatim}
{
  "v": 1,
  "ts": "2024-02-10T15:30:45.123Z",
  "channel_values": {
    "messages": [...],
    "firmware_project_dir": "/tmp/stm32_project",
    "model_path": "/cache/mobilenet_v2.h5",
    "route": "ai_flow",
    "nni_search_space": {...}
  },
  "parent_config": {
    "configurable": {
      "thread_id": "michele:vscode-session",
      "checkpoint_id": "1707575432123"
    }
  }
}
\end{verbatim}

where \textbf{key fields} are \texttt{channel\_values} which contains the complete \texttt{MasterState} object with all 50+ attributes, \texttt{parent\_config} which is the reference to the previous checkpoint (for time-travel) and \texttt{ts} which is the timestamp for ordering checkpoints.

\subsection{Server-Side Profile Management}

The long-term memory layer is manually managed in \texttt{server.py}.

\subsubsection{Profile Loading}

Before executing the graph, the server loads the user profile from Redis and injects it into the \texttt{initial\_state}:

\begin{lstlisting}[language=Python, caption={User profile loading in server.py}, label={lst:profile_load}]
# 1. Construct profile key
user_profile_key = f"user:{request.user_id}:profile"

# 2. Fetch from Redis
raw_profile = await redis_client.get(user_profile_key)
user_profile = json.loads(raw_profile) if raw_profile else {}

# 3. Inject into initial state
initial_state = {
    "message": last_user_message,
    "persistent_context": user_profile,
    "reset_profile": False
}
\end{lstlisting}

The \texttt{persistent\_context} field is accessible to all graph nodes, enabling context-aware decisions.

\subsubsection{Profile Saving}

After workflow completion (or critical state mutations), the profile is updated:

\begin{lstlisting}[language=Python, caption={User profile saving in server.py}, label={lst:profile_save}]
# 1. Extract current values from state
new_profile = {
    "board_name": state.get("board_name"),
    "mcu_series": state.get("mcu_series"),
    "last_model": state.get("selected_model"),
    "last_project_path": state.get("firmware_project_path") or state.get("firmware_project_dir"),
    "last_workflow": state.get("route"),
    "timestamp": state.get("timestamp")
}

# 2. Update profile dictionary
new_profile = {k: v for k, v in new_profile.items() if v is not None and v != ""}
updated_profile = {**user_profile, **new_profile}

# 3. Serialize and save to Redis
await redis_client.set(user_profile_key, json.dumps(updated_profile))
\end{lstlisting}

The \texttt{ex} (expiration) parameter prevents indefinite accumulation of inactive user profiles.

\subsection{Context Chaining Across Sessions}

The dual-memory architecture enables powerful cross-session workflows:

\subsubsection{Example: Multi-Day NNI Experiment}

\textbf{Day 1 - Session 1 (VS Code):}
\begin{enumerate}
  \item User: ``@stm32ai run NNI experiment on MobileNetV2 for Fruit-360''
  \item Framework launches NNI (20 trials, estimated 12 hours)
  \item After 2 hours, user closes VS Code
  \item \textbf{Short-Term Memory} saves checkpoint: \texttt{route = "nni\_optimization"}, \texttt{nni\_status = "running"}
  \item \textbf{Long-Term Memory} saves: \texttt{last\_board = "STM32H7"}, \texttt{session\_count++}
\end{enumerate}

\textbf{Day 2 - Session 2 (CLI):}
\begin{enumerate}
  \item User reconnects via CLI with same \texttt{user\_\allowbreak id + session\_\allowbreak id}
  \item \texttt{graph.aget\_state(config)} retrieves the checkpoint from Day 1
  \item \textbf{Automatic Resume}: The graph detects \texttt{current\_\allowbreak state.next = ["check\_\allowbreak nni\_\allowbreak status"]} and resumes execution
  \item NNI results are retrieved from disk, best model is saved, and integration proceeds
\end{enumerate}

\subsubsection{Example: Board Preference Pre-Fill}

\textbf{Session A (Firmware Generation):}
\begin{enumerate}
  \item User: ``Create project for STM32H743''
  \item Firmware generated successfully
  \item Profile updated: \texttt{last\_board = "STM32H743ZI"}
\end{enumerate}

\textbf{Session B (AI Model Selection, 1 week later):}
\begin{enumerate}
  \item User: ``Analyze MobileNetV2''
  \item \textbf{Context Chaining}: The \texttt{collect\_\allowbreak analysis\_\allowbreak info()} node checks \texttt{state.last\_board} and auto-populates \texttt{target\_mcu = "stm32h743"}
  \item No need for user to re-specify hardware → \textbf{Eliminated 1 clarification roundtrip}
\end{enumerate}

\subsection{HITL Resume Logic}

The short-term memory checkpoint enables continuous Human-in-the-Loop workflows:

\subsubsection{Interrupt Flow}

\begin{enumerate}
  \item Node calls \texttt{interrupt(\{type: "decision\_request", message: "Proceed to AI?"\})}
  \item LangGraph suspends execution and saves checkpoint with \texttt{next = ["decide\_\allowbreak continue\_\allowbreak to\_\allowbreak ai"]}
  \item Control returns to API server, which sends a JSON event to VS Code
  \item User sees: ``Firmware generated. Continue with AI model selection? [Yes/No]''
\end{enumerate}

\subsubsection{Resume Flow}

\begin{enumerate}
  \item User types: ``Yes, use high compression''
  \item VS Code sends \texttt{POST /stream} with \texttt{messages: [\{role: "user", content: "Yes, use high compression"\}]}
  \item Server calls \texttt{graph.aget\_state(config)} and detects \texttt{current\_\allowbreak state.next = ["decide\_\allowbreak continue\_\allowbreak to\_\allowbreak ai"]}
  \item Server injects user response: \texttt{await graph.aupdate\_\allowbreak state(config, \{"user\_\allowbreak response": "Yes, use high compression"\})}
  \item Graph resumes from \texttt{decide\_\allowbreak continue\_\allowbreak to\_\allowbreak ai} node, which parses the response via LLM and routes accordingly
\end{enumerate}

\subsection{Performance Considerations}

\subsubsection{Redis I/O Overhead}

Checkpoint writes inherently add latency to the execution pipeline, typically in the range of 5 to 20 milliseconds per node transition. To mitigate this overhead, the framework employs several strategies, such as the use of non-blocking asynchronous I/O operations in the \texttt{AsyncRedisSaver} to prevent main event loop stalls. Furthermore, network transit latency is minimized during development by defaulting to a local \texttt{redis://localhost} connection. LangGraph further optimizes this process by consolidating multiple internal state updates from a single node's execution context into a single write operation before transitioning to the next stage of the graph.

\subsubsection{Memory Footprint and Evolution of Data Persistence}

During early development, the system attempted to store large artifacts (such as generated firmware zips, serialized models, and base64 images) directly within the Redis state. However, this approach presented technical bottlenecks, as Redis string size limits and synchronization overhead slowed down the orchestration loop.

To resolve this, the architectural design evolved toward a hybrid persistence model using \textbf{Container Persistent Volumes}. Instead of using an intermediate database for heavy files, the system writes artifacts directly to persistent storage volumes mapped to individual container instances. This strategy perfectly aligns with a Cloud-Native architecture: in a future Kubernetes deployment, each user will operate within a dedicated namespace with dynamically provisioned PersistentVolumeClaims (PVCs).

Redis is now strictly limited to maintaining the lightweight conversational checkpointing of the LangGraph execution thread, while the storage of project files is handled natively by the file system. This simplifies the architecture, improves I/O performance, and guarantees environment isolation without relying on database abstractions.

\subsection{Security Considerations}

Given that user profiles may store sensitive information, such as STMicroelectronics developer credentials required for STEdgeAI cloud authentication, the framework must adhere to strict security practices. In production deployments, it is imperative to encrypt sensitive fields using solid algorithms like AES-256 before persisting them in the Redis data store.

Also, access control should be strictly enforced using Redis ACL (Access Control Lists) to restrict client permissions, ensuring that specific key patterns (e.g., \texttt{user:*:profile}) are only accessible to authenticated and authorized services.

Finally, to comply with GDPR data minimization principles and prevent indefinite data retention, user profiles are configured with a Time-To-Live (TTL) expiration policy, ensuring they are automatically purged after one year of complete inactivity.
