\section{Neural Network Customization Workflow}
\label{sec:customization}

Once a base model has been discovered and profiled, the user may need to adapt its architecture to meet specific hardware constraints, retarget its output to a new set of classes, or improve its accuracy on a domain-specific dataset. Workflow 5 implements a customization pipeline that breaks this process into five stages: model inspection, best practice retrieval, interactive modification planning, architecture patching, and fine-tuning. The implementation is contained in \texttt{workflow5\_customization.py} and runs as a LangGraph graph with conditional routing between nodes.

\subsection{Model Architecture Inspection}

The workflow begins with the \texttt{inspect\_\allowbreak model\_\allowbreak architecture()} node, which analyses the downloaded model file and populates the graph state with the architectural metadata needed by all subsequent steps. The extracted data includes layer types (Conv2D, Dense, Dropout), output shapes, the total parameter count, and whether the model contains BatchNormalization or Dropout layers. This profile feeds directly into the best practice retrieval and modification planning steps.

Model loading is not a trivial operation: the same file can fail with a standard \texttt{load\_model()} call if it was saved with a different Keras version or if it contains custom objects. For this reason, the node implements a three-level fallback chain. In the first attempt, it calls \texttt{tf.keras.models.load\_model()} with \texttt{compile=False} and reads the architecture directly from the live model object. If that fails on a \texttt{.h5} or \texttt{.keras} file, the node switches to a raw HDF5 inspection: it opens the file with \texttt{h5py} and parses the \texttt{model\_config} attribute to recover the layer list and names without loading any weights. If both attempts fail, the node fills the state with a minimal default dictionary (all counts set to zero, format set to \texttt{unknown}) so that the pipeline can still continue and present the user with a fallback interface.

Files in \texttt{.onnx} or \texttt{.tflite} format are handled separately. Since these formats do not expose a Keras layer graph, the node sets a generic metadata block and sets the format field accordingly. The user is informed that structural customization (layer editing and fine-tuning) is not available for these formats; the workflow then routes them directly to the STEdgeAI analysis step.

After inspection, the results are also checked against the idempotency flag: if the architecture data is already present from a previous Workflow 2 run, the node skips the loading step entirely.

\subsection{Best Practice Retrieval}
\label{sec:best_practices}

Before asking the user to specify modifications, the system retrieves a tailored set of fine-tuning recommendations for the detected architecture. The \texttt{retrieve\_\allowbreak best\_\allowbreak practices\_\allowbreak for\_\allowbreak architecture()} function follows a three-step strategy, moving to the next step only if the previous one fails.

First, it checks whether a ChromaDB vectorstore already exists for the identified architecture type (e.g., \texttt{mobilenet}, \texttt{resnet}, \texttt{yolo}). Each architecture has its own persistent collection stored under \texttt{st\_\allowbreak ai\_\allowbreak output/chroma\_\allowbreak docs/}. If the collection exists and returns results with a similarity score above the threshold, those documents are used immediately, avoiding any LLM call.

If no cached data is found, the system invokes the local Ollama LLM (Mistral) to generate a concise best practice guide. The prompt is deliberately structured and constrained, requesting a bullet-point output with four specific sections (strategy, hyperparameters, quantization, and memory constraints), and keeps the response under 200 tokens. The generated document is then split into chunks and saved to the architecture-specific ChromaDB collection for reuse:

\begin{lstlisting}[language=Python, caption={LLM-based best practice generation and caching}, label={lst:rag_gen}]
llm = get_llm(None, temperature=0.3, keep_alive="5m")
prompt = f"""You are an expert embedded AI engineer.
Provide a concise, bullet-point checklist for fine-tuning
{model_name} ({arch_type}) on STM32.
Keep it under 200 words. Schematic only."""

response = llm.invoke(prompt)
doc = Document(page_content=response.content,
               metadata={"source": "LLM_GENERATED",
                         "architecture": arch_type})
Chroma.from_documents([doc], embeddings,
                       persist_directory=persist_dir,
                       collection_name=f"{arch_type}_best_practices")
\end{lstlisting}

If even the LLM call fails (for example, due to an Ollama timeout), the function falls back to a set of hardcoded, architecture-specific guidance texts compiled into the module. Each entry covers the typical layer-freezing ratio, recommended learning rate range, quantization considerations for STM32, and any known constraints specific to that architecture. For example, the VGG entry warns explicitly that the architecture is memory-heavy and may not fit many STM32 targets even after INT8 quantization.

\subsection{Modification Intent Classification}

The \texttt{ask\_\allowbreak modification\_\allowbreak intent()} node determines, without mandatory user input, whether the current request requires any architectural changes. It first analyses the initial message sent to start the workflow. If the text contains explicit modification keywords (e.g., ``freeze'', ``dropout'', ``change input'') with a confidence above 90\%, the node sets \texttt{wants\_\allowbreak model\_\allowbreak modifications = True} and skips the interrupt. Generic triggers like ``analyze'' or ``start ai'' are treated as negative signals regardless of confidence, since those phrases imply the user wants to proceed without changes.

When the intent is ambiguous or entirely absent, the node pauses with an LangGraph interrupt and presents a structured prompt:

\begin{lstlisting}[language=Python, caption={Modification intent classification schema}, label={lst:intent}]
class ModificationDecision(BaseModel):
    wants_modifications: bool
    reasoning: str
    confidence: float = Field(ge=0.0, le=1.0)

llm_classifier = get_llm(config).with_structured_output(ModificationDecision)
decision = llm_classifier.invoke([
    SystemMessage(content=modification_decision_instructions),
    HumanMessage(content=f"User response: {user_text}")
])
\end{lstlisting}

If the user replies negatively, the graph routes to the STEdgeAI analysis step directly, bypassing all customization nodes. The persistent context is also checked: if the user ran a customization in the previous session, the prompt displays a reminder suggesting they might want to do so again.

\subsection{Modification Parsing and Validation}
\label{sec:mod_parsing}

When modifications are requested, the \texttt{ask\_\allowbreak and\_\allowbreak parse\_\allowbreak user\_\allowbreak modifications()} node collects the user's natural language description and converts it into a structured plan using the \texttt{ParsedModificationsPlan} Pydantic schema. The schema captures a list of individual modifications, an overall confidence score, training recommendations (learning rate, batch size, epochs, optimizer), and a validation sub-object listing any detected issues.

The node supports seven distinct modification types:

\begin{itemize}[noitemsep, topsep=4pt]
  \item \textbf{freeze\_layers}: Freezes the first $N$ layers of the model, preserving pre-trained features.
  \item \textbf{freeze\_almost\_all}: Leaves only the last $N$ layers trainable, useful for fast adaptation.
  \item \textbf{change\_output\_layer}: Replaces the final Dense layer to match a new number of target classes.
  \item \textbf{add\_dropout}: Inserts a Dropout layer before the output, with a user-specified rate.
  \item \textbf{change\_input\_shape}: Rebuilds the model with a different input resolution by patching the model config via \texttt{Model.from\_config()}.
  \item \textbf{change\_learning\_rate}: Sets a custom learning rate, stored in the training recommendation field.
  \item \textbf{add\_resizing\_layer}: Wraps the existing model in a new input layer that accepts images of any resolution and resizes them automatically to the model's original input shape. This is the only valid option for detection models (YOLO, SSD) where changing the input shape directly would break the output grid structure.
\end{itemize}

The LLM extractor is called with strict instructions to parse only what the user explicitly asked for. A second validation pass then checks each modification for parameter completeness and value ranges (for example, dropout rates must be between 0.0 and 1.0, and the layer count must not exceed the total layers in the model). The \texttt{change\_\allowbreak input\_\allowbreak shape} type is also cross-checked against a blocklist of model families for which it is unsupported:

\begin{lstlisting}[language=Python, caption={Input shape compatibility guard}, label={lst:input_guard}]
INCOMPATIBLE_INPUT_SHAPE_MODELS = {
    'yolo': ['tiny_yolo_v2', 'yolov2', 'yolov3', 'yolov4'],
    'ssd':  ['ssd_mobilenet', 'st_ssd_mobilenet_v1'],
    'time_series_models': ['gmp', 'har', 'activity_recognition'],
}
\end{lstlisting}

If a blocked modification is detected, it is removed from the plan, a warning is added to the validation issues list, and the user is advised to use \texttt{add\_\allowbreak resizing\_\allowbreak layer} instead.

\subsection{Preview and Confirmation}

Before any file is modified, the \texttt{collect\_\allowbreak modification\_\allowbreak confirmation()} node displays a structured preview to the user: a summary of all planned modifications, the overall confidence of the parsing, the training recommendations, and any validation warnings. The user can respond in one of three ways: confirm the plan, reject it entirely, or request changes. The response is interpreted by an LLM agent, with a keyword-based fallback parser in case the LLM call fails.

If the user asks to revise the plan, the graph sets \texttt{user\_\allowbreak wants\_\allowbreak to\_\allowbreak edit = True} and routes back to the modification parsing node, allowing a full re-specification without restarting the workflow.

\subsection{Architecture Patching}
\label{sec:arch_patching}

Once the plan is confirmed, the \texttt{apply\_\allowbreak user\_\allowbreak customization()} node patches the model architecture in a subprocess. Before starting, the node resolves the correct conda environment based on the model format: \texttt{.keras} files are processed in the \texttt{stm32} environment (Keras 3.x), while \texttt{.h5} files use \texttt{stm32legacy} (Keras 2.x). This routing is necessary because most models downloaded from common repositories are saved in the legacy HDF5 format, which is incompatible with Keras 3's default importer.

The patching itself is divided into two phases. Non-reconstructive modifications, that is layer freezing and learning rate changes, are applied directly to the model object in memory since they do not alter the graph topology. Reconstructive modifications, those that change the layer graph (output size, dropout injection, input shape, resizing wrapper), are queued and then applied in a specific order to preserve skip connections:

\begin{enumerate}[noitemsep, topsep=4pt]
  \item \textbf{Output layer change}: The model config dict is patched to update the units count of the last Dense layer, and the model is rebuilt with \texttt{Model.from\_config()}. Weights from all layers except the last Dense are copied to the new model.
  \item \textbf{Dropout insertion}: A Dropout layer is inserted between the penultimate layer and the output layer using the functional API.
  \item \textbf{Input shape change}: The \texttt{batch\_\allowbreak input\_\allowbreak shape} field of the first layer's config is patched, and the entire model is rebuilt. Weights are copied where shapes allow; layers with a shape mismatch are re-initialized.
  \item \textbf{Resizing wrapper}: A new \texttt{Input} layer accepting \texttt{(None, None, C)} is created, a \texttt{Resizing} layer is appended to scale images to the model's original resolution, and the existing model is called on the resized output.
\end{enumerate}

The entire patching script runs in a subprocess via \texttt{execute\_\allowbreak in\_\allowbreak environment()}, which writes the script to a temporary file, runs it with the selected Python binary, and streams output line by line. A \texttt{SUCCESS:} marker in stdout signals that the modified model was saved to \texttt{/tmp/customized\_model.h5} along with a JSON-encoded info block.

\subsection{Standard Fine-Tuning Path}
\label{sec:standard_fine_tuning}

The \texttt{fine\_\allowbreak tune\_\allowbreak customized\_\allowbreak model()} node fine-tunes the patched model on the user's dataset inside another subprocess (using the \texttt{stm32} conda environment). The training configuration is taken from the \texttt{training\_recommendation} field of the parsed modification plan, with two safety caps applied: the learning rate is clipped at \texttt{1e-3} to avoid destabilizing pre-trained weights, and the epoch count is capped at 10 for standard runs.

The node supports two dataset sources. When \texttt{dataset\_source = "real"}, it loads \texttt{x\_train.npy} and \texttt{y\_train.npy} from the configured dataset path, normalises pixel values to $[0, 1]$, applies one-hot encoding if the labels are in scalar format, and limits the sample count to 5,000 to avoid RAM exhaustion. If a separate \texttt{x\_test.npy} exists, it is used as the validation split. When \texttt{dataset\_source = "synthetic"}, the node generates random noise data instead. If neither option is available, it falls back to pure dummy data so that the training step always completes and the user gets a functional model file, even without a dataset.

Before training begins, the node detects class count mismatches automatically. If the number of unique labels in the dataset differs from the model's output size (a common situation when adapting a 1000-class ImageNet model to a 5-class custom task), the final Dense layer is replaced on the fly without requiring the user to re-run the modification step:

\begin{lstlisting}[language=Python, caption={Automatic class mismatch correction during fine-tuning}, label={lst:class_fix}]
if dataset_num_classes != model_num_classes:
    base_output = model.layers[-2].output
    dropout = tf.keras.layers.Dropout(dropout_rate)(base_output)
    new_output = tf.keras.layers.Dense(
        dataset_num_classes, activation='softmax'
    )(dropout)
    model = tf.keras.Model(inputs=model.input, outputs=new_output)
\end{lstlisting}

Images are also resized in batches of 500 if the loaded data shape does not match the model's expected input, handling grayscale-to-RGB conversion along the way.

\subsection{NNI Code Generation: Architecture and Prompt Engineering}

The main technical contribution of this workflow is the autonomous generation of complete NNI experiment code from high-level specifications. Instead of using rigid templates, the system employs a large language model to dynamically synthesize Python scripts. These scripts address complex cases such as sparse versus categorical label formats, input shape mismatches requiring dynamic image resizing, and class count discrepancies.

The generated code also manages memory limits on consumer hardware through dataset subsetting and memory-mapping, resolves port conflicts for the NNI Web UI, and includes fallbacks for missing NNI API methods across different library versions.

\subsubsection{Prompt Engineering Strategy}

The \texttt{generate\_\allowbreak nni\_\allowbreak experiment()} function in \texttt{nni\_optimization/generator.py} uses a detailed 480-line prompt to produce accurate generation. This prompt relies on context injection by providing the LLM with exact model metadata, such as layer counts and tensor shapes, together with specific dataset requirements. To prevent common errors, the instructions forbid the use of placeholder paths or the reference of non-existent API methods. It also includes functional code templates for both \texttt{manager.py} and \texttt{trial.py}, with inline comments explaining the most significant logic blocks.

Specific rules are included to address known inconsistencies in the NNI API. For example, the prompt explicitly warns that \texttt{experiment.get\_\allowbreak best\_\allowbreak trial()} is unavailable in certain versions. To ensure the output remains easy to parse, the system also mandates a strict format using \texttt{\# FILE:} markers for multi-file generation.

A representative extract from the prompt:

\begin{verbatim}
CRITICAL REQUIREMENTS:
- Generate exactly 2 files: manager.py AND trial.py
- Use the exact format shown below with # FILE: markers
- DO NOT use keras.datasets.load_data(). Load data from {dataset_path}.
- If labels (y_train) have shape (N, 1), they are SPARSE.
  Convert them to categorical (one-hot) before training.

FILE 1: manager.py
- Configure NNI (TPE tuner, maximize mode)
- Define search space (learning_rate, batch_size, optimizer)
- Launch with experiment.run(port=8080, wait_completion=True)
- Find best trial via experiment.list_trial_jobs() only
- Trigger retrain: run trial.py with RETRAIN_MODE='true'

FILE 2: trial.py
- Load model and data from provided paths
- MEMORY OPTIMIZATION: Load data with mmap_mode='r'
- DATASET SUBSET: Use only 50% of the dataset
- Adapt final layer if class count mismatches
- Do NOT use experiment.export_top_trial() -- it does not exist.
\end{verbatim}

The LLM temperature is set to 0 for deterministic code generation. Before generation starts, the Triton LLM model is explicitly unloaded from GPU to free VRAM for the TensorFlow training process:

\begin{lstlisting}[language=Python, caption={Triton model unloading before NNI generation}, label={lst:gpu_cleanup}]
def force_unload_triton(model_name: str = "mistral"):
    url = f"http://localhost:8000/v2/repository/models/{model_name}/unload"
    req = urllib.request.Request(url, method='POST')
    try:
        with urllib.request.urlopen(req) as response:
            logger.info(f"Triton model '{model_name}' unloaded.")
    except Exception as e:
        logger.error(f"Failed to unload Triton model: {e}")
\end{lstlisting}

This call runs in the \texttt{finally} block of \texttt{generate\_\allowbreak nni\_\allowbreak experiment()} so that VRAM is released regardless of whether generation succeeds or fails.

\subsubsection{Multi-File Parser}

The LLM output is a single string containing both files, separated by \texttt{\# FILE: filename.py} markers. The \texttt{extract\_\allowbreak files\_\allowbreak from\_\allowbreak code()} function parses it with a permissive regex:

\begin{lstlisting}[language=Python, caption={Multi-file code extraction}, label={lst:file_extraction}]
file_pattern = re.compile(
    r'^\#\s*FILE:\s*([a-zA-Z0-9_\-\.]+)',
    re.MULTILINE | re.IGNORECASE
)
\end{lstlisting}

The parser handles common variations in the raw output string. It ignores optional spacing around the hash or \texttt{FILE:} markers, strips away markdown code fences (like \texttt{```python}), and identifies trailing comments mistaken for part of the filename.

If no markers are found, the output is saved as \texttt{main.py} as a fallback for single-file tasks.

\subsubsection{Generated File Structure}

\paragraph{\texttt{manager.py}}
This file manages the hyperparameter search. It sets up CUDA library paths for Conda environments, defines the NNI search space (learning rate, batch size, optimizer, freeze backbone flag), configures the TPE tuner, scans for a free port in the 8080--8100 range to avoid conflicts, and launches the experiment with \texttt{experiment.run(wait\_completion=True)}. After all trials complete, it manually iterates \texttt{experiment.list\_\allowbreak trial\_\allowbreak jobs()} to find the highest-accuracy trial, then re-runs \texttt{trial.py} with \texttt{RETRAIN\_MODE=true} to produce the final saved model.

\paragraph{\texttt{trial.py}}
This file executes a single training trial. It checks the \texttt{RETRAIN\_MODE} environment variable to determine whether to report metrics back to NNI or save the final model. Data is loaded with \texttt{mmap\_mode='r'}, meaning NumPy maps the files directly from the disk rather than loading the entire dataset into RAM. This optimization is crucial for NNI: if multiple training trials run concurrently, loading the dataset independently for each process would quickly saturate system memory, resulting in an Out-of-Memory (OOM) crash. Instead, it creates a virtual pointer directly to the file stored on the SSD. Data is then read in small blocks only at the exact moment it is needed by the neural network for training. The 'r' stands for "read-only", ensuring that the training process cannot accidentally corrupt the original dataset.
Furthermore, only 50\% of the data is used per trial to strictly bound memory usage. If the label array has shape \texttt{(N, 1)}, it is converted to one-hot automatically. If the model's output class count does not match the dataset, the final Dense layer is replaced in-place. Images are resized dynamically if the input shape mismatches, and data augmentation (random flips, rotations, zoom) is applied during training.

\subsection{Hyperparameter Optimization Execution}

Once the NNI scripts are successfully generated and saved to \texttt{./nni\_experiment/}, the training is started by \texttt{optimize\_\allowbreak hyperparameters\_\allowbreak with\_\allowbreak nni()}:

\begin{enumerate}[noitemsep, topsep=2pt]
  \item \textbf{Validation}: Checks that both \texttt{manager.py} and \texttt{trial.py} exist and are syntactically valid Python.
  \item \textbf{Subprocess Launch}: Spawns \texttt{python manager.py} in a separate process to avoid blocking the LangGraph event loop.
  \item \textbf{Output Streaming}: Captures stdout/stderr in real-time for user feedback.
  \item \textbf{Completion Detection}: Waits for subprocess termination (blocking until experiment finishes).
  \item \textbf{Model Retrieval}: Locates \texttt{best\_model.h5} in the NNI output directory and stores path in state.
\end{enumerate}

The subprocess execution isolates NNI's environment from the LangGraph runtime, preventing library conflicts and allowing independent GPU scheduling.

Algorithm~\ref{alg:nni_retrain} outlines the NNI workflow, including the extraction of the best trial and retraining.

\begin{algorithm}[H]
  \caption{NNI Experiment with Automatic Best-Trial Retraining}
  \label{alg:nni_retrain}
  \begin{algorithmic}[1]
    \REQUIRE Model path $M$, dataset path $D$, search space $S$, max trials $N$
    \ENSURE Retrained best model saved to disk
    \STATE $experiment \gets \text{NNI\_Create}(\text{tuner}=\text{``TPE''}, S, N)$
    \STATE $experiment.\text{run}(\text{wait\_completion}=\text{true})$
    \STATE \COMMENT{Extract best trial manually (stable API-agnostic method)}
    \STATE $trials \gets experiment.\text{list\_trial\_jobs}()$
    \STATE $valid\_trials \gets \{t \in trials \mid t.\text{status} = \text{``SUCCEEDED''}\}$
    \IF{$|valid\_trials| = 0$}
    \STATE \textbf{error} ``No successful trials''
    \ENDIF
    \STATE $best\_trial \gets \arg\max_{t \in valid\_trials} t.\text{finalMetricData}[0].\text{data}$
    \STATE $best\_params \gets best\_trial.\text{hyperParameters}[-1].\text{parameters}$
    \STATE \COMMENT{Retrain with best hyperparameters}
    \STATE $env \gets \{\text{``RETRAIN\_MODE''}: \text{``true''}, \text{``NNI\_PARAMS''}: \text{JSON}(best\_params)\}$
    \STATE $\text{subprocess.run}([\text{``python'', ``trial.py''}], \text{env}=env)$
    \STATE $best\_model \gets \text{Load}(\text{``best\_model.h5''})$
    \RETURN $best\_model$
  \end{algorithmic}
\end{algorithm}

\subsection{Validation and Model Persistence}

After NNI completes, the \texttt{validate\_\allowbreak customized\_\allowbreak model()} node loads \texttt{best\_model.h5} and evaluates it on a held-out test set. If validation accuracy meets the user's threshold (configurable, default 0.7), the model is saved alongside a JSON metadata file:

\begin{lstlisting}[language=Python, caption={Model persistence with metadata tracking}, label={lst:model_save}]
metadata = {
    "base_model": state.model_path,
    "customization_date": datetime.now().isoformat(),
    "nni_search_space": state.nni_search_space,
    "best_hyperparameters": state.best_hyperparameters,
    "validation_accuracy": final_accuracy,
}

model.save(output_path)
with open(output_path.replace('.h5', '_metadata.json'), 'w') as f:
    json.dump(metadata, f, indent=2)
\end{lstlisting}

This metadata file links the final model to the hyperparameters that produced it and to the base model it was derived from, which supports reproducibility and simplifies future analysis.
