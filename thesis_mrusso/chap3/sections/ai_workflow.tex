\section{The Core Orchestrator (LangGraph)}

\subsection{AI Model Discovery and Validation Workflow}
\label{sec:ai_flow}

Workflow 2 handles the selection, profiling, and C code generation of pre-trained neural networks for STM32 microcontrollers (see Figure~\ref{fig:detailed_flowchart_part1} for the entry routing logic). Embedded AI differs from conventional MLOps in one fundamental respect: raw accuracy is only one metric among several. RAM, Flash, and MACC budgets set hard physical limits that constrain every design choice. The workflow addresses this by combining a curated local registry with iterative web search and delegating quantization decisions to the STEdgeAI toolchain.

\subsubsection{Analysis Parameters Collection}

\texttt{collect\_\allowbreak analysis\_\allowbreak info()} extracts the target MCU and the desired compression level from the user's message. The node scans the initial prompt for known MCU series tokens (e.g., \texttt{h7}, \texttt{u5}, \texttt{f4}). If nothing is found, it issues an interrupt and surfaces the last used series from the persistent context as a suggestion. When Workflow 1 has already set \texttt{state.target} from the selected board, the interrupt is skipped entirely. Inference is delegated to \texttt{get\_llm()}, which routes requests to the NVIDIA Triton Inference Server when \texttt{USE\_\allowbreak TRITON\_\allowbreak BACKEND} is set, falling back to a local Ollama instance otherwise:

\begin{lstlisting}[language=python, caption={Parameter extraction from user input}, label={lst:param_extraction}]
# User: "I need a model for image classification on STM32H7 with high compression"

llm_extractor = get_llm(
    config=config,
    structured_schema=AnalysisInfoExtraction,
    temperature=0
)
result = llm_extractor.invoke([
    SystemMessage(content=analysis_info_extraction_instructions),
    HumanMessage(content=f"Risposta utente: {user_text}")
])

# result.target = "stm32h743"
# result.compression = "high"
\end{lstlisting}

Both values are stored in \texttt{MasterState} and reused across model selection, profiling, and code generation without being re-parsed.

\subsubsection{Three-Tier Model Discovery Architecture}

Model discovery follows a three-tier hierarchy. The first tier covers locally curated catalogs, the second runs automated web searches, and the third allows users to register their own models. Each tier is tried in order, and the process terminates as soon as the user confirms a candidate.

\subsubsection{Tier 1: Curated Task-Based Models (Two-Node Pipeline)}

The first tier runs across two separate nodes. \texttt{choose\_\allowbreak ai\_\allowbreak task()} presents a menu of all task categories in \texttt{predefined\_models.json}, a JSON registry decoupled from the discovery logic so it can be updated without touching any source code. The menu covers standard embedded tasks (image classification, object detection, human activity recognition) and also exposes two shortcut options: ``Register your own model'' and ``Online search''. An LLM classifier maps the user's free-text response to the appropriate category key.

\texttt{choose\_\allowbreak ai\_\allowbreak model()} then handles selection within the chosen category. Before showing the list, it computes a compatibility estimate for each model by comparing its stated file size against the flash limit returned by \texttt{get\_\allowbreak mcu\_\allowbreak limits(state.target)}:

\begin{itemize}[noitemsep, topsep=4pt]
    \item Models fitting within flash limits natively are marked \textbf{Fits} ($\checkmark$)
    \item Models that can be compressed to fit are marked \textbf{Compressible} with the size ratio shown
    \item Models too large even at maximum compression are flagged \textbf{Too Large} ($\times$)
\end{itemize}

The user sees this information upfront, before any download or conversion is attempted.

\subsubsection{Tier 2: Iterative Web Search with Hybrid Retrieval}

When no curated model satisfies the request, the system enters \texttt{search\_\allowbreak recommendation\_\allowbreak model()}, a loop capped at three iterations. Each iteration tries two backends in sequence.

The primary backend scans the \texttt{STMicroelectronics/stm32ai-modelzoo} GitHub repository via the PyGitHub API. It recursively traverses the task-specific subfolder (depth limit: 5, early exit at 20 files) and collects files with extensions \texttt{.h5}, \texttt{.keras}, \texttt{.onnx}, or \texttt{.tflite}. An LLM then scores each candidate on task relevance, architecture recognition, and file size, and the top result is validated with a lightweight HTTP HEAD check before being shown to the user.

The secondary backend is a DuckDuckGo-based web search, tried only if GitHub yields nothing. Importantly, it does not consume an iteration, so a failed GitHub scan followed by a successful web result leaves the full three-iteration budget intact.

After either backend finds a candidate, the node issues a LangGraph interrupt for explicit user approval:

\begin{lstlisting}[language=python, caption={User confirmation interrupt after each candidate}, label={lst:search_confirm}]
user_confirmation = interrupt({
    "instruction": f"""Model found: {model_name} ({ext}, {size})
URL: {url_raw}

Accept this model? (yes/no)
- 'yes': Proceed to download
- 'no': Continue searching"""
})
\end{lstlisting}

A rejection resets \texttt{state.model\_\allowbreak discovery\_\allowbreak method} to \texttt{"search"} and the routing node re-enters the loop. After three failed iterations, the system selects a task-based fallback from the local registry and presents it with one final confirmation interrupt before starting the download.

\subsubsection{Tier 3: User Model Registration}

Users can also register their own local or remote models through \texttt{add\_\allowbreak custom\_\allowbreak model\_\allowbreak procedure()}, providing a category, a name, and a direct download URL. The entry is written to \texttt{predefined\_models.json} only after \texttt{stedgeai analyze} confirms the model is structurally valid for the target runtime.

\subsubsection{Model Download and Inspection}

\texttt{download\_\allowbreak model\_\allowbreak to\_\allowbreak cache()} saves the selected model to \texttt{\textasciitilde/.stm32\_\allowbreak ai\_\allowbreak models/}. A cached copy, if present, is reused without re-downloading. For fresh downloads, data streams in 8~KB chunks with progress logged every 20\%. The file size is checked after saving, and if the model entry carries an optional \texttt{sha256} field, the hash is verified before proceeding.

Architecture inspection follows a two-level subprocess strategy. The model is loaded inside an isolated subprocess in the correct conda environment (\texttt{stm32} for \texttt{.keras}, \texttt{stm32legacy} for \texttt{.h5}). The inspection script is generated inline as a Python string and executed via \texttt{execute\_\allowbreak in\_\allowbreak environment()}; results are returned through a \texttt{JSON\_\allowbreak START\ldots JSON\_\allowbreak END} marker in stdout:

\begin{lstlisting}[language=python, caption={Inline subprocess script for model inspection}, label={lst:legacy_env}]
script = f"""
import tensorflow as tf, json, sys

try:
    model = tf.keras.models.load_model(r'{model_path}', compile=False)
    info = {{
        'input_shape': str(model.input_shape),
        'n_layers': len(model.layers),
        'total_params': int(model.count_params()),
        'has_batchnorm': any(['BatchNormalization' in
            l.__class__.__name__ for l in model.layers]),
    }}
    print("JSON_START" + json.dumps(info) + "JSON_END")
except Exception as e:
    print(f"ERROR:{{e}}")
    sys.exit(1)
"""
res = execute_in_environment(script, python_path, timeout=30)
\end{lstlisting}

If the subprocess fails, a second pass opens the file with \texttt{h5py} and reads the raw HDF5 metadata without loading any weights. The extracted metadata is stored in \texttt{state.model\_architecture} for use by Workflow 5.

\subsubsection{STEdgeAI CLI Integration}

With a model in hand, the workflow runs a three-phase profiling and code generation cycle using the STEdgeAI toolchain. An optional fine-tuning and customization step may precede this phase; it is described separately in Section~\ref{sec:customization}.

\subsubsection{Phase 1: Model Analysis}

\texttt{run\_analyze()} calls the STEdgeAI analysis engine to estimate resource consumption on the target MCU:

\begin{verbatim}
stedgeai analyze --model <model.h5> --target <stm32h743>
                 --output ./analisiAI/report_analyze
\end{verbatim}

The resulting report covers RAM usage (tensor buffers, activation memory, working memory), Flash usage after quantization (Flash is the non-volatile program memory that stores the quantized model weights and the generated C inference code), MACC count per inference (number of multiply-accumulate operations, the standard metric for neural network computational cost), and estimated latency at typical clock speeds. If RAM or Flash limits are exceeded, the node automatically increments the quantization aggressiveness from \texttt{medium} to \texttt{high} and repeats the command, continuing until the model fits or the maximum compression level is reached.

\subsubsection{Phase 2: On-Target Validation}

\texttt{run\_validate()} produces a validation report for the target architecture:

\begin{verbatim}
stedgeai validate --model <model.h5> --target <stm32h743>
                  --output ./analisiAI/network_validate_report.txt
\end{verbatim}

The report confirms model integrity, that activation buffers fit within target RAM, and that all operators are supported on the specific MCU series.

\subsubsection{Phase 3: C Code Generation}

\texttt{run\_generate()} produces the final inference artifacts:

\begin{verbatim}
stedgeai generate --model <model.h5> --target <stm32h743>
                  --compression <high> --output ./analisiAI/code_resnet
\end{verbatim}

Output includes \texttt{network.c/h} (fixed-point neural network implementation), \texttt{network\_data.c} (quantized weights as const arrays), and \texttt{network\_config.h} (MCU-specific memory layout and hardware acceleration flags). Quantization is applied here via \texttt{--compression}, not during training. This lets the framework evaluate models in full-precision FP32 and defer bit-width decisions until the exact MCU constraints are known from Phase 1.

\subsubsection{Legacy Model Handling with Dual-Environment Strategy}

Modern Keras 3.x, required by LangGraph and NNI, is incompatible with the Keras 2.x models widespread in STModelZoo and academic repositories. Rather than forcing a single environment, the framework maintains two separate conda installations:

\begin{itemize}
    \item \textbf{Primary environment} (\texttt{stm32}): hosts LLM agents, LangGraph, and NNI with the latest dependencies
    \item \textbf{Legacy environment} (\texttt{stm32legacy}): pinned to TensorFlow 2.15 and Keras 2.15 for inspection and fine-tuning of older model files
\end{itemize}

At download time, \texttt{download\_\allowbreak model\_\allowbreak to\_\allowbreak cache()} reads the file extension and routes accordingly: \texttt{.keras} files go to \texttt{stm32}, while \texttt{.h5} files are directed to \texttt{stm32legacy} via the \texttt{ARCH\_\allowbreak ENVIRONMENT\_\allowbreak MAP} dictionary, which also maps specific architectures (e.g., YOLO variants) to their required environment. The chosen interpreter path is resolved from the system configuration and passed to \texttt{execute\_\allowbreak in\_\allowbreak environment()}, keeping the main runtime isolated from TensorFlow dependency conflicts.
