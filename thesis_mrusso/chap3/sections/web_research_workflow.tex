\subsection{Web Research Workflow for Technical Guidance}
\label{sec:web_research}

Workflow 4 provides technical research on demand. It queries the web and synthesizes the results into a structured summary. We avoided routing requests through a static knowledge base. Instead, the workflow runs live DuckDuckGo searches across four distinct domains and evaluates the summary quality using DeepEval.

\subsection{Request Classification}

Before any search is issued, the \texttt{classify\_search()} node determines what kind of information the user needs. A structured LLM call using \texttt{get\_llm()} classifies the request into one of four categories: \texttt{ai\_model} (finding neural network models compatible with STM32), \texttt{board\_selection} (comparing MCU families), \texttt{optimization} (quantization and compression techniques), and \texttt{documentation} (tutorials, guides, official references). Requests that fall outside these categories are labelled \texttt{none} and routed to a clarification step instead.

From the user's natural language message the node extracts both the category and a refined English search query, which is constructed to be specific enough for a web search engine. A reasoning field explains the classification decision and is logged for debugging.

\subsection{Dynamic Search Execution}

The routing node \texttt{search\_\allowbreak type\_\allowbreak decision()} confirms the category is valid, then passes control to \texttt{execute\_\allowbreak web\_\allowbreak search()}, a single node that handles all four domains. The choice of a unified node rather than four separate ones keeps the graph compact: the appropriate prompt template is selected at runtime from the \texttt{SEARCH\_PROMPTS} dictionary by indexing on \texttt{state.search\_type}.

Each prompt template instructs the agent on the specific fields to retrieve. For AI model searches, for instance, the template asks for model name, framework, size in KB, compatible STM32 targets, quantization level, and inference benchmarks. For board comparisons it requests flash, RAM, clock speed, peripheral sets, and price.

The native Python \texttt{duckduckgo-search} library executes the search. It fetches up to six webpage snippets, extracting titles, bodies, and source URLs. We deliberately removed complex function-calling wrappers to maintain compatibility with Triton. The backend now handles standard inference requests without needing native tool-calling integrations.

\begin{lstlisting}[language=Python, caption={Direct DuckDuckGo search execution without tool-calling overhead}]
from duckduckgo_search import DDGS

with DDGS() as ddgs:
    results = list(ddgs.text(state.search_query, max_results=6))
    for r in results:
        snippet = f"**{r.get('title', '')}**\n{r.get('body', '')}\nSource: {r.get('href', '')}"
        raw_results.append(snippet)
\end{lstlisting}

The raw aggregated text is stored in \texttt{state.search\_results}. It is then split into paragraph-level chunks (filtered to at least 20 characters) and saved to \texttt{state.search\_\allowbreak results\_\allowbreak list}, which feeds the evaluation stage.

\subsection{Summarization}

After the search, \texttt{summarize\_\allowbreak search\_\allowbreak results()} condenses the raw content into a structured answer. A single LLM call (via \texttt{get\_llm()}, temperature 0.2) is given the original query and up to 10,000 characters of web results. The prompt instructs the model to produce a technically focused answer in English, use bullet points for readability, cite source URLs where present, and explicitly state when the retrieved content is not relevant to the query. The resulting summary is stored in \texttt{state.search\_summary} and displayed to the user by the final \texttt{finalize\_search()} node.

\subsection{Quality Evaluation with DeepEval}

Once the summary is ready, the \texttt{finalize\_search()} node runs an automated quality assessment using the \textbf{DeepEval} framework. Evaluation runs synchronously in a separate thread (via \texttt{asyncio.to\_thread}) to avoid blocking the event loop. All four metrics run on a local \texttt{OllamaModel} backed by \texttt{deepseek-r1:latest}, keeping evaluation fully offline. The 0.55 threshold serves exclusively as an observability and logging baseline calibrated for local model capabilities. It does not act as a blocking filter; instead, if a metric falls below this threshold, the framework simply records a "Fail" status for offline analysis without discarding any sources or interrupting the runtime:

\begin{itemize}
    \item \textbf{Faithfulness}: checks that claims in the summary are supported by the retrieved text (threshold: 0.55)
    \item \textbf{Answer Relevancy}: measures how well the summary addresses the original query (threshold: 0.55)
    \item \textbf{Contextual Relevancy}: assesses whether the retrieved documents were topically appropriate (threshold: 0.55)
    \item \textbf{Hallucination}: detects content in the summary absent from the retrieval context (threshold: 0.55)
\end{itemize}

Each metric is measured independently; failures in one do not abort the others. Scores are printed to the console alongside the summary. If the evaluation framework itself raises an exception (e.g., due to a missing dependency or model timeout), the error is logged as a warning and the workflow completes normally without blocking the user.
