Installa Xvfb (se non già presente):

bash

La flag -a di xvfb-run sceglie automaticamente un display libero, ed evita l’eccezione HeadlessException. Questo è il metodo più semplice per usare CubeMX CLI su un server senza interfaccia grafica.
Dove:
X11 è il sistema completo per la grafica su Linux.
Xvfb è un server X11 virtuale che crea un display “fittizio” in memoria, usato per far girare programmi grafici in assenza di un vero schermo, utile per test, automazione, CI/CD, e ambienti server senza GUI.

1. Lanciato STM32CubeMX in modalità "headless" su un server Linux
xvfb-run -a crea un ambiente grafico virtuale (X11 “headless” display), necessario perché STM32CubeMX è una app Java che anche in modalità CLI richiede la presenza di un display X11.
Questo permette di eseguire STM32CubeMX senza vera GUI anche in ambienti server o continous integration privi di desktop environment.​
2. Esegue STM32CubeMX con lo "script" di comandi (modalità quiet -q)
Il flag -q avvia CubeMX in "quiet mode" (= nessuna finestra, nessuna interazione utente).​
CubeMX legge il file comando /mnt/shared-storage/mrusso/cubemx15/cubescript.txt. Questo contiene istruzioni come:

project toolchain ...
project path ...
project generate
exit

Crea il progetto con il nome specificato.
Setta la toolchain di destinazione (tipicamente STM32CubeIDE ma puoi indicare altre toolchain supportate).

Genera il codice di startup C (periferiche, clock, pin, HAL, etc.), i file .ioc e la struttura del progetto (cartelle Src, Inc, etc.).

Il problema è che sul server si blocca a project generate perché:
Problema
STM32CubeMX fatica a generare correttamente e completamente un progetto su filesystem come:
Google Drive virtuale (es. drive montato come G:\ su Windows)
Filesystem di rete (NFS, SMB, storage condiviso tipo /mnt/shared-storage/)
Questi filesystem hanno caratteristiche che interferiscono con il modo di lavorare di CubeMX:
Gestione particolare o non standard dei file lock
Ritardi e latenza nelle operazioni di I/O
Gestione diversa dei permessi e dei metadati dei file
Meccanismi di caching e sincronizzazione che possono creare conflitti temporanei
Questi fattori possono causare che la generazione del progetto sia:
Incompleta (mancano file .c, .h, struttura progetto)
Bloccata o interrotta senza errori chiari
Non riconosciuta correttamente da CubeIDE
Un esempio pratico è dato da chi si è spostato da Google Drive al disco locale C:\ ed è riuscito a far funzionare la generazione, mentre prima falliva.
Perché funziona così?
CubeMX genera tantissimi file piccoli con frequenti accessi e modifiche in sequenza, cosa che:
Su filesystem locali (disco SSD o HDD) è veloce e stabile
Su filesystem di rete o unità virtuali (Google Drive) può diventare instabile e lento, con rischi di lock o fallimenti
Quindi la miglior pratica è separare la fase di generazione (locale) dalla fase di archiviazione/sincronizzazione (rete/virtuale).

In python:
python
import subprocess
import os
import shlex
import tempfile
import time
class STM32CubeMXAutomator:
    def __init__(self, cubemx_path, shared_storage_base):
        self.cubemx_path = cubemx_path
        self.shared_storage_base = shared_storage_base
    def run_command(self, cmd, timeout=None):
        """Run a shell command and return (exit_code, stdout, stderr)."""
        process = subprocess.Popen(
            cmd, shell=True,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True
        )
        try:
            out, err = process.communicate(timeout=timeout)
        except subprocess.TimeoutExpired:
            process.kill()
            out, err = process.communicate()
        return process.returncode, out, err
    def generate_project(self, mcu, project_name, toolchain, ioc_file=None):
        # 1. Prepare temp directory
        temp_dir = tempfile.mkdtemp(prefix="stm32_")
        script_path = os.path.join(temp_dir, "cubemx_script.txt")
        # 2. Write CubeMX batch script
        with open(script_path, "w") as f:
            f.write(f"load {mcu}\n")
            if ioc_file:
                f.write(f'config load "{ioc_file}"\n')
            f.write(f"project name {project_name}\n")
            f.write(f'project toolchain "{toolchain}"\n')
            f.write(f"project path {temp_dir}\n")
            f.write("project generate\n")
            f.write("exit\n")
        # 3. Run CubeMX headless via Xvfb
        cmd = f"xvfb-run -a {shlex.quote(self.cubemx_path)} -q {shlex.quote(script_path)}"
        code, out, err = self.run_command(cmd, timeout=300)
        if code != 0:
            raise RuntimeError(f"CubeMX failed:\nSTDOUT:\n{out}\nSTDERR:\n{err}")
        # 4. Copy to shared storage
        dest = os.path.join(self.shared_storage_base, project_name)
        os.makedirs(os.path.dirname(dest), exist_ok=True)
        # Remove old if exists
        subprocess.run(f"rm -rf {shlex.quote(dest)}", shell=True)
        subprocess.run(f"cp -r {shlex.quote(temp_dir)}/{shlex.quote(project_name)} {shlex.quote(dest)}", shell=True)
        # 5. Cleanup
        subprocess.run(f"rm -rf {shlex.quote(temp_dir)}", shell=True)
        return dest
if __name__ == "__main__":

Un agente LangGraph potrebbe invocare questa funzione Python come tool, passandole i parametri (MCU, nome progetto, percorso .ioc), e riceverne in risposta il path del progetto generato o un errore.
Questa automazione Python non apre alcun terminale grafico:
Tutti i comandi (mkdir, xvfb-run, cp, rm) vengono eseguiti in background tramite la libreria subprocess di Python, senza interfaccia utente.
Non viene “aperta” una shell visibile: Python lancia direttamente i processi nel sistema, catturandone output e errori.
Su Linux headless, non serve né funziona aprire un terminale grafico: xvfb-run fornisce un display X virtuale in memoria, invisibile, su cui gira STM32CubeMX.
In pratica, l’agente/sistema esegue tutto “in background” sul server, non c’è nessuna finestra di terminale visibile.

Cosa significa X11 forwarding?
Tutte le applicazioni grafiche avviate sul server remoto (ad esempio STM32CubeMX, xclock, xeyes, gedit ecc.) avranno la loro interfaccia visualizzata sul tuo desktop locale come se fossero app locali, anche se in realtà girano nel server remoto.
I dati grafici, finestre e interazione, viaggiano criptati attraverso il tunnel SSH dal server al tuo PC.
Quando e perché si usa?
Utile quando vuoi manipolare software che richiede un'interfaccia grafica ma il server non ha un monitor locale, o tu sei distante.
Non serve configurare un monitor esterno né usare VNC: basta che la tua macchina locale abbia un server X (XQuartz per Mac, X11 per Linux, MobaXterm/Xming per Windows).

Ecco un nodo LangGraph completo che fa esattamente quello:
python
# ============================================================================
# STM32 PACKAGE DISCOVERY AND INSTALLATION
# ============================================================================
class PackageSearchResult(BaseModel):
    """Risultato della ricerca di un package ST su GitHub"""
    package_found: bool = Field(description="Se il package è stato trovato su GitHub")
    github_url: Optional[str] = Field(default=None, description="URL del repository GitHub")
    board_series: Optional[str] = Field(default=None, description="Serie MCU (L4, F4, H7, etc.)")
def search_and_install_stm32_package(state: MasterState, config: dict) -> MasterState:
    """
    Nodo che ricerca il package ST appropriato su GitHub in base al board_name,
    lo clona, estrae i file XML, li copia nel database CubeMX e pulisce.
    """
    
    logger.info("🔍 Ricerca package STM32 su GitHub...")
    
    cfg = Configuration.from_runnable_config(config)
    cubemx_db = os.path.join(os.path.dirname(cfg.cubemx_path), "db", "mcu")
    
    # Estrai la serie MCU dal board_name
    board_series = extract_mcu_series(state.board_name)
    
    if not board_series:
        logger.error(f"❌ Non riesco a estrarre la serie da: {state.board_name}")
        state.package_installation_success = False
        state.package_error_message = f"Serie MCU non riconosciuta da {state.board_name}"
        return state
    
    logger.info(f"📊 Serie MCU estratta: {board_series}")
    
    # Map serie → URL GitHub
    GITHUB_PACKAGES = {
        "F0": "https://github.com/STMicroelectronics/STM32CubeF0.git",
        "F1": "https://github.com/STMicroelectronics/STM32CubeF1.git",
        "F2": "https://github.com/STMicroelectronics/STM32CubeF2.git",
        "F3": "https://github.com/STMicroelectronics/STM32CubeF3.git",
        "F4": "https://github.com/STMicroelectronics/STM32CubeF4.git",
        "F7": "https://github.com/STMicroelectronics/STM32CubeF7.git",
        "H7": "https://github.com/STMicroelectronics/STM32CubeH7.git",
        "L0": "https://github.com/STMicroelectronics/STM32CubeL0.git",
        "L1": "https://github.com/STMicroelectronics/STM32CubeL1.git",
        "L4": "https://github.com/STMicroelectronics/STM32CubeL4.git",
        "L5": "https://github.com/STMicroelectronics/STM32CubeL5.git",
        "U5": "https://github.com/STMicroelectronics/STM32CubeU5.git",
        "G0": "https://github.com/STMicroelectronics/STM32CubeG0.git",
        "G4": "https://github.com/STMicroelectronics/STM32CubeG4.git",
        "H5": "https://github.com/STMicroelectronics/STM32CubeH5.git",
        "W5": "https://github.com/STMicroelectronics/STM32CubeW5.git",
        "C0": "https://github.com/STMicroelectronics/STM32CubeC0.git",
    }
    
    github_url = GITHUB_PACKAGES.get(board_series)
    
    if not github_url:
        logger.error(f"❌ Package non trovato per serie {board_series}")
        state.package_installation_success = False
        state.package_error_message = f"Nessun package GitHub per serie {board_series}"
        return state
    
    logger.info(f"🎯 Package trovato: {github_url}")
    
    # Path temporanei
    clone_path = f"/tmp/STM32Cube{board_series}"
    
    try:
        # === 1. CLONE RICORSIVO ===
        
        logger.info(f"📥 Clone ricorsivo dal repository...")
        cmd_clone = ["git", "clone", "--recursive", github_url, clone_path]
        
        result = subprocess.run(cmd_clone, capture_output=True, text=True, timeout=600)
        
        if result.returncode != 0:
            logger.error(f"❌ Clone fallito!")
            logger.error(f"Stderr: {result.stderr}")
            raise RuntimeError(f"Git clone failed: {result.stderr}")
        
        logger.info(f"✓ Repository clonato: {clone_path}")
        
        # === 2. RICERCA FILE XML ===
        
        logger.info(f"🔎 Ricerca file XML...")
        xml_files = []
        for root, dirs, files in os.walk(clone_path):
            for file in files:
                if file.endswith('.xml'):
                    xml_files.append(os.path.join(root, file))
        
        logger.info(f"✓ Trovati {len(xml_files)} file XML")
        
        if len(xml_files) == 0:
            logger.warning(f"⚠️  Nessun file XML trovato")
            state.package_installation_success = False
            state.package_error_message = "Nessun file XML trovato nel repository"
            return state
        
        # === 3. COPIA FILE XML NEL DATABASE CUBEMX ===
        
        logger.info(f"📂 Copia file XML nel database CubeMX...")
        copied_count = 0
        
        for xml_file in xml_files:
            try:
                filename = os.path.basename(xml_file)
                dest_path = os.path.join(cubemx_db, filename)
                shutil.copy2(xml_file, dest_path)
                logger.info(f"  ✓ {filename}")
                copied_count += 1
            except Exception as e:
                logger.warning(f"  ⚠️  Non posso copiare {os.path.basename(xml_file)}: {e}")
        
        logger.info(f"✓ Copiati {copied_count}/{len(xml_files)} file")
        
        # === 4. VERIFICA ===
        
        logger.info(f"✅ Verifica installazione...")
        verify_cmd = f"ls {cubemx_db}/STM32{board_series}*.xml 2>/dev/null | wc -l"
        verify_result = subprocess.run(verify_cmd, shell=True, capture_output=True, text=True)
        count = int(verify_result.stdout.strip())
        
        logger.info(f"✓ {count} device XML installati per serie {board_series}")
        
        if count > 0:
            state.package_installation_success = True
            logger.info(f"✓ Package {board_series} installato con successo!")
        else:
            state.package_installation_success = False
            state.package_error_message = "Copia completata ma verifica fallita"
        
    except Exception as e:
        logger.error(f"❌ Errore durante installazione: {str(e)}")
        logger.exception(e)
        state.package_installation_success = False
        state.package_error_message = str(e)
    
    finally:
        # === 5. CLEANUP ===
        
        logger.info("🧹 Cleanup file temporanei...")
        
        try:
            if os.path.exists(clone_path):
                logger.info(f"Rimozione: {clone_path}")
                shutil.rmtree(clone_path)
                logger.info(f"  ✓ Cartella rimossa")
        except Exception as e:
            logger.warning(f"  ⚠️  Non posso cancellare {clone_path}: {e}")
        
        logger.info("✓ Cleanup completato")
    
    return state

Cosa genera stedgeai generate?
Partendo da un modello grande (100MB):
text
ResNet50 (PyTorch)
├─ 100+ milioni di parametri
├─ Pesi FP32 (4 byte per peso)
├─ Size: ~100MB
└─ Performance: GPU richiesta per inference
                ↓ STEdgeAI (Quantizzazione INT8)
                
ResNet50 Quantizzato
├─ 100+ milioni di parametri (ridotti)
├─ Pesi INT8 (1 byte per peso, 4x più piccolo!)
├─ Size: ~25MB (ridotto)
├─ Performance: Ancora GPU (x10 più veloce)
                ↓ STEdgeAI (Ottimizzazione STM32)
                
network.c / network_data.c (Embedded C)
├─ Pesi precompressi e ottimizzati
├─ Funzioni C specifiche per STM32 (ARM NEON, intrinsics)
├─ Size: ~300KB
├─ Performance: CPU pura (no GPU, ma in tempo reale!)
├─ Latenza: 50-200ms per inference (STM32H7)
└─ Ready to integrate in firmware

// Funzione di inference ottimizzata per ARM
ai_status_t ai_network_run(ai_network_t* net, const uint8_t* input, uint8_t* output) {
    
    float conv1_out[112*112*64];     // Activation layer 1
    float relu1_out[112*112*64];     // After ReLU
    float pool1_out[56*56*64];       // After pooling
    // ...
    
    // Layer 1: Convolution 7x7, stride 2
    ai_conv2d_opt_int8(
        input, 224, 224, 3,           // Input: 224x224x3
        ai_network_weights,            // Weights
        conv1_out,                     // Output
        7, 2, 64                       // Filter 7x7, stride 2, 64 filters
    );
    
    // Layer 2: ReLU activation
    ai_relu(conv1_out, relu1_out, 112*112*64);
    
    // Layer 3: Max pooling 3x3, stride 2
    ai_maxpool2d(relu1_out, 112, 112, 64, pool1_out, 3, 2);
    
    // ... Continua per tutte le layer ...
    
    // Output finale: 1000 classi
    return AI_OK;
}
💻 Come Si Usa nel Firmware
main.c (Codice utente con AI integrato)
c
#include "main.h"
#include "network.h"              // ← AI model header
#include "network_data.h"          // ← AI weights
// Global AI network instance
ai_network_t network = {0};
// Camera input buffer (224x224x3 RGB)
uint8_t camera_frame[224*224*3];
// AI output buffer (1000 class probabilities)
uint8_t ai_predictions[1000];
void main(void) {
    // 1. Initialize STM32 hardware
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_CAMERA_Init();
    MX_UART_Init();
    
    // 2. Initialize AI network
    network.weights = (float*)ai_network_weights;
    network.biases = (float*)ai_network_biases;
    network.input_size = 224*224*3;
    network.output_size = 1000;
    
    while(1) {
        // 3. Capture frame from camera
        HAL_CAMERA_GetFrame(camera_frame);
        
        // 4. Run AI inference
        uint32_t start = HAL_GetTick();
        ai_network_run(&network, camera_frame, ai_predictions);
        uint32_t latency_ms = HAL_GetTick() - start;
        
        // 5. Process results
        uint8_t top_class = find_max_class(ai_predictions);
        float confidence = ai_predictions[top_class] / 255.0f;
        
        // 6. Output results
        printf("Class: %d, Confidence: %.2f%%, Latency: %d ms\n",
               top_class, confidence*100, latency_ms);
        
        // 7. Optional: Take action based on prediction
        if (top_class == PERSON_CLASS && confidence > 0.8f) {
            HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, GPIO_PIN_SET);
        }
    }
}

 Problema - Dal log:
 "Unrecognized keyword arguments passed to DepthwiseConv2D: {'groups': 1}"
 Succede perché:
 -Il modello STM32 usa DepthwiseConv2D con parametro groups=1
 -La tua versione Keras 3 NON riconosce groups in DepthwiseConv2D
 -Keras di default (safe_mode=True) è RIGIDO e blocca tutto ciò che non capisce
 -Con safe_mode=False Keras è PIÙ PERMISSIVO e prova a caricare comunque. Consente deserializzazione di DepthwiseConv2D con groups anche se sconosciuto e permette layer personalizzati di STM32.
 con safe_mode=False dice : OK: è STM32 ufficiale, non malevolo
 però non va lo stesso...
Problema: file .h5 STM32 salvati con Keras < 3.x contengono parametro 'groups=1' che la versione nuova non riconosce. 
Ma cosa si intende per ‘groups’?
Ti spiego cosa significa groups e perché crea problemi.
Cos'è il Parametro groups in DepthwiseConv2D
groups è un parametro delle convoluzioni gruppate che specifica in quanti sottogruppi indipendenti dividere i canali di input durante la convoluzione.
Concetto Base
Convoluzione Normale (groups=1):
text
Input:    [H, W, 3 canali RGB]
         
Kernel:   [3×3 filtro che vede TUTTI i 3 canali]
         
Output:   [H, W, N filtri di output]
```
Ogni filtro riceve tutti i 3 canali RGB come input.
Grouped Convolution (groups=N):
groups=3
Canale 1 → Filtro gruppo 1 → Output canale 1Canale 2 → Filtro gruppo 2 → Output canale 2 (SEPARATI!)Canale 3 → Filtro gruppo 3 → Output canale 3
Input: [H, W, 3] → ogni canale processato INDIPENDENTEMENTE
text
Ogni gruppo di canali viene elaborato isolatamente.
 Nel Tuo Caso: DepthwiseConv2D
DepthwiseConv2D (convoluzione in profondità) è un caso speciale dove:
groups = numero_di_canali_input
Esempio con 32 canali:groups=32 → ogni canale ha 1 filtro proprio
Input: [H, W, 32 canali]
Filtri: 32 filtri (1 per canale)
Output: [H, W, 32 canali]
text
Ogni canale NON interagisce con gli altri.
 Il Problema Nel Tuo File .h5
Il tuo modello STM32 (MobileNetV2) è stato salvato con Keras 2.x che includeva il parametro `groups` nella config:
``````json
{
  "class_name": "DepthwiseConv2D",
  "config": {
    "name": "expanded_conv_depthwise",
    "kernel_size": [3, 3],
    "strides": [1, 1],
    "groups": 1,          ← ⚠️ PROBLEMA!
    "depth_multiplier": 1,
    ...
  }
}
Quando provi a caricarlo con Keras 3.x, la versione nuova non riconosce questo parametro perché l'ha rimosso dalla firma della funzione:
python
Keras 2.x - Accettava 'groups'
class DepthwiseConv2D(Layer):def init(self, groups=1, ...):  ← accetta groupspass
Keras 3.x - NON accetta 'groups'
class DepthwiseConv2D(Layer):def init(self, ...):  ← NO 'groups' parameterpass
text
Quindi quando Keras 3.x legge la config del file e trova `"groups": 1`, genera l'errore:
ValueError: Unrecognized keyword arguments passed to DepthwiseConv2D: {'groups': 1}
text
 La Soluzione: Rimuovere `groups` dalla Config
Ecco cosa fa la funzione nel codice che ti ho passato:
```python```
def remove_groups_recursive(obj):
    """Rimuovi 'groups' da TUTTI i layer della config"""
    if isinstance(obj, dict):
        obj.pop('groups', None)   ← RIMUOVI 'groups' se presente
        for v in obj.values():
            remove_groups_recursive(v)   Ricorsivo: vai dentro ai dicts
    elif isinstance(obj, list):
        for item in obj:
            remove_groups_recursive(item)   Ricorsivo: vai dentro agli arrays

Prima (config corrotta):
json
{
  "layers": [
    {
      "class_name": "DepthwiseConv2D",
      "config": {
        "groups": 1,
        "kernel_size": [3, 3],
        ...

 Perché è Sicuro Rimuovere `groups`?
Per DepthwiseConv2D è completamente sicuro perché:
1. DepthwiseConv2D = sempre grouped convolution: il comportamento è hardcoded nel layer
2. Il parametro è ridondante: DepthwiseConv2D SA che deve essere `groups = num_canali`
3. Non cambia il significato: la rimozione del parametro dalla config non modifica cosa il layer fa
Esempio con modello MobileNetV2:
``````python
 PRIMA (Keras 2.x config)
DepthwiseConv2D(groups=32, depth_multiplier=1)
 ↓ Comportamento: ogni canale elaborato indipendentemente
 DOPO (Keras 3.x config pulita)
DepthwiseConv2D(depth_multiplier=1)
 ↓ Comportamento: IDENTICO! (depthwise è sempre così)
```

def detect_and_load_model(model_path: str) -> Optional[tf.keras.Model]:
    """
    Carica modello intelligentemente:
    1. Rilevamento architettura dai layer names
    2. Se standard → load weights diretto
    3. Se custom → ricostruzione manuale o fallback
    """
    
    with h5py.File(model_path, 'r') as f:
        layer_names = list(f['model_weights'].keys())
    
     ===== RILEVAMENTO ARCHITETTURA =====
    
    if any('block_' in name for name in layer_names) and any('depthwise' in name for name in layer_names):
        logger.info("🔍 Detected: MobileNetV2")
        model = tf.keras.applications.MobileNetV2(weights=None)
    
    elif any('res' in name for name in layer_names) and any('branch' in name for name in layer_names):
        logger.info("🔍 Detected: ResNet")
        model = tf.keras.applications.ResNet50(weights=None)
    
    elif any('block' in name for name in layer_names) and 'conv' in layer_names[0]:
        logger.info("🔍 Detected: VGG")
        model = tf.keras.applications.VGG16(weights=None)
    
    elif any('mixed' in name for name in layer_names):
        logger.info("🔍 Detected: InceptionV3")
        model = tf.keras.applications.InceptionV3(weights=None)
    
    else:
        logger.warning("⚠️  Unknown architecture, attempting generic load...")
         Tenta standard load come fallback
        model = tf.keras.models.load_model(model_path, compile=False, safe_mode=False)
        if model is None:
            logger.error("❌ Cannot determine architecture")
            return None
    
     ===== CARICA PESI =====
    logger.info("  Loading weights...")
    model.load_weights(model_path, by_name=True, skip_mismatch=True)
    
    return model

    // Crea e inizializza la rete
    network = ai_network_create_and_init(NULL);
    
    if (!network) {
        Error_Handler();
    }
}
ai_error AI_Run_Inference(
    uint8_t *input_image,           // 224×224×3
    float *output_predictions,      // 1000 classi
    uint32_t *predicted_class       // Classe vincente
)
{
    ai_error err;
    ai_tensor input_tensor;
    ai_tensor output_tensor;
    
    // Setup input tensor
    input_tensor.data = input_image;
    input_tensor.size = 224 * 224 * 3;
    
    // Setup output tensor  
    output_tensor.data = output_predictions;
    output_tensor.size = 1000;
    
    // RUN INFERENCE (blocca per ~34 ms)
    uint32_t timestamp = HAL_GetTick();
    err = ai_network_run(network, &input_tensor, &output_tensor);
    uint32_t inference_time = HAL_GetTick() - timestamp;
    
    if (err != AI_ERROR_NONE) {
        return err;
    }
    
    // Post-processing: find class with max probability
    float max_prob = 0.0f;
    uint32_t max_class = 0;
    
    for (uint32_t i = 0; i < 1000; i++) {
        if (output_predictions[i] > max_prob) {
            max_prob = output_predictions[i];
            max_class = i;
        }
    }
    
    *predicted_class = max_class;
    
    // Log timing
    HAL_UART_Transmit(
        &huart2,
        (uint8_t*)"Inference: %d ms, Class: %d, Conf: %.1f%%\r\n",
        inference_time, max_class, max_prob * 100
    );
    
    return AI_ERROR_NONE;
}
// Main loop
void main_loop(void)
{
    AI_Init();  // Inizializza rete
    
    uint8_t image_buffer[224*224*3];
    float predictions[1000];
    uint32_t class_id;
    
    while (1)
    {
        // Leggi frame da camera via DCMI
        Camera_CaptureFrame(image_buffer);
        
        // Preprocessing (normalizzazione, conversione formato)
        PreprocessImage(image_buffer);
        
        // Inference
        AI_Run_Inference(image_buffer, predictions, &class_id);
        
        // Delay per prossimo frame (~50 ms per 20 FPS)
        HAL_Delay(50);
    }
}

Differenza tra 'ADD RESIZE PREPROCESSING' e 'CHANGE INPUT SHAPE'
1. CHANGE INPUT SHAPE
Modifica la configurazione dell'input del modello Keras.
Cambia la shape che il modello si aspetta come input esplicitamente, ad esempio da (224, 224, 3) a (64, 64, 3).
Tutte le operazioni convolutive, stride, padding, shortcut, ecc., all'interno della rete lavorano effettivamente con questa nuova risoluzione.*
Di solito richiede la ricostruzione architetturale del modello e il settaggio (o re-init/copy) dei pesi.
Lo shape degli input che passi a model.predict()/model.fit() DEVE essere esattamente quello nuovo.
Esempio di impatto:
Cambiare input shape di MobileNet da 224x224 a 64x64 significa che tutte le feature maps interne saranno ridotte (tutto il modello viene effettivamente applicato su 64x64).
2. ADD RESIZE PREPROCESSING
Non modifica la configurazione d'input reale del modello: lascia invariato lo shape input della rete (es: (224, 224, 3)). 
Aggiunge un layer Resizing all'inizio del modello. Questo layer prende qualunque input (ad esempio, (128, 128, 3)) e lo converte a (224, 224, 3) tramite interpolazione.
Dal punto di vista della rete, lo shape che vede "realmente" è sempre il vecchio.
Gli altri layer e tutti i pesi rimangono esattamente come sono, NON c'è bisogno di ricostruire il grafo.
L'utente/gateway può passare al modello immagini di qualunque dimensione: il layer Resizing le trasforma sempre nel formato atteso dalla rete.
Esempio di impatto:
Input di qualunque dimensione (64x64, 128x128, 300x300) verrà ridimensionato a 224x224x3 PRIMA che entri nella vera rete.
💡 Quando usare l'uno o l'altro
Change Input Shape:Usalo solo se vuoi realmente cambiare l'operatività del modello sull'intero grafo per ragioni di memoria o efficienza (es. porting su microcontrollore).
Add Resize Preprocessing:Usalo se vuoi solo flessibilità sugli input (puoi facilmente inferire immagini di dimensioni qualsiasi) e vuoi mantenere le prestazioni/originalità/robustezza del modello pre-addestrato.
ADD RESIZE PREPROCESSING è più sicuro perché:
✅ Non cambia l'architettura interna
✅ Nessun rischio di mismatch negli Add layer
✅ Nessun bisogno di ricopia pesi
✅ Funziona con input di qualunque dimensione
CHANGE INPUT SHAPE è più rischioso perché:
❌ Cambia gli stride interni
❌ Causa shape mismatch negli Add/Concatenate layer
❌ Richiede ricopia pesi complessa
❌ Valore agli Add layer dipende dalla nuova shape

def prepare_user_dataset(state: MasterState, config: dict) -> MasterState:
    """
    ✨ Carica, valida e prepara il dataset per fine-tuning
    """
    
    logger.info("🔍 Preparando dataset utente...")
    
    try:
        dataset_path = state.user_dataset_path
        dataset_format = state.user_dataset_format
        
        if not os.path.exists(dataset_path):
            logger.error(f"❌ Dataset not found: {dataset_path}")
            state.dataset_ready = False
            state.error_message = "Dataset not found"
            return state
        
        dataset_dir = '/tmp/user_dataset_extracted'
        os.makedirs(dataset_dir, exist_ok=True)
        
         ===== ESTRAI DATASET =====
        if dataset_format == "zip_with_classes":
            import zipfile
            logger.info("  Extracting ZIP file...")
            with zipfile.ZipFile(dataset_path, 'r') as zip_ref:
                zip_ref.extractall(dataset_dir)
        
        elif dataset_format == "folder_with_classes":
            logger.info("  Copying folder structure...")
            import shutil
            shutil.copytree(dataset_path, dataset_dir, dirs_exist_ok=True)
        
         ===== VALIDA STRUTTURA =====
        logger.info("  Validating dataset structure...")
        
        classes = state.user_dataset_classes
        dataset_info = {
            "total_samples": 0,
            "classes": {},
            "input_shape": None,
        }
        
        for class_name in classes:
            class_dir = os.path.join(dataset_dir, class_name)
            
            if not os.path.exists(class_dir):
                logger.error(f"❌ Class directory not found: {class_name}")
                state.dataset_ready = False
                state.error_message = f"Class directory missing: {class_name}"
                return state
            
            num_images = len([f for f in os.listdir(class_dir) if f.endswith(('.jpg', '.png', '.jpeg'))])
            dataset_info["classes"][class_name] = num_images
            dataset_info["total_samples"] += num_images
            
            logger.info(f"  ✓ {class_name}: {num_images} images")
        
        if dataset_info["total_samples"] == 0:
            logger.error("❌ No images found in dataset")
            state.dataset_ready = False
            state.error_message = "No images found"
            return state
        
        state.user_dataset_path = dataset_dir
        state.dataset_info = dataset_info
        state.dataset_ready = True
        
        logger.info(f"\n✅ Dataset ready!")
        logger.info(f"  Total samples: {dataset_info['total_samples']}")
        logger.info(f"  Classes: {len(classes)}")
        
    except Exception as e:
        logger.error(f"❌ Dataset preparation failed: {str(e)}", exc_info=True)
        state.dataset_ready = False
        state.error_message = str(e)
    
    return state

Dense layer in una rete neurale a cosa serve?
Dense layer (livello denso) serve a combinare tutti gli input disponibili per estrarre e rappresentare pattern complessi nei dati, grazie a neuroni pienamente connessi con pesi e bias addestrabili. In pratica è il “layer standard” delle reti feedforward, usato sia negli strati nascosti sia spesso come strato finale di classificazione o regressione.
Cos’è un dense layer
Un dense layer è composto da  neuroni, ognuno dei quali riceve come input tutti i valori in uscita dallo strato precedente (fully connected). Ogni neurone calcola una combinazione lineare degli input (somma pesata più bias) e poi applica una funzione di attivazione come ReLU, sigmoide o tanh per introdurre non linearità.​
A cosa serve nella rete
Lo scopo principale è imparare una trasformazione dei dati che renda più facile il compito finale (classificazione, regressione, ecc.) modellando relazioni anche non lineari tra le feature. Per questo viene usato come strato nascosto “generico” nelle MLP e come testa fully connected sopra feature estratte da CNN o altre architetture.​
Effetti pratici
Maggiore capacità espressiva: con abbastanza neuroni e layer densi, la rete può approssimare funzioni molto complesse.​
Costo e overfitting: essendo completamente connessi, introducono molti parametri, quindi aumentano costo computazionale e rischio di overfitting, spesso mitigato con regolarizzazione o dropout.

Training , validation , evaluation cosa cambia?
Nel machine learning, la distinzione tra Training, Validation ed Evaluation (Test) è fondamentale per garantire che il modello non si limiti a memorizzare i dati (overfitting) ma sia capace di generalizzare su nuovi input.
In sintesi: il Training serve a imparare i parametri (pesi), il Validation serve a ottimizzare gli iperparametri e scegliere il modello migliore, mentre l’Evaluation serve a stimare le prestazioni reali finali senza bias.
Ecco nel dettaglio cosa cambia tra le tre fasi:
1. Training Set (Addestramento)
È il set di dati più voluminoso ed è l'unico che il modello "vede" direttamente per modificare i suoi parametri interni.
Scopo: Aggiornare i pesi (weights) e i bias della rete neurale o i coefficienti dell'algoritmo tramite backpropagation e discesa del gradiente.
Cosa succede qui: Il modello cerca di minimizzare la loss function su questi dati specifici.codecademy+1​
2. Validation Set (Validazione / Tuning)
È un set di dati separato usato durante l'addestramento, ma non viene usato per aggiornare direttamente i pesi.
Scopo: Fornire una stima imparziale delle prestazioni del modello mentre si trova ancora in fase di sviluppo. Serve per il tuning degli iperparametri (es. learning rate, numero di layer, dimensione del kernel) e per l'Early Stopping (interrompere il training se la validation loss smette di scendere).kili-technology+1​
Differenza chiave: Influenza il modello indirettamente. Se modifichi l'architettura o gli iperparametri basandoti sui risultati di questo set, stai tecnicamente introducendo un bias verso questi dati.techtarget​
3. Evaluation / Test Set (Valutazione Finale)
È un set di dati che viene tenuto completamente "in cassaforte" fino alla fine del progetto.
Scopo: Simulare come il modello si comporterà nel mondo reale una volta distribuito.
Regola d'oro: Non deve mai essere usato per prendere decisioni durante il training o il tuning. Se lo usi per scegliere il modello migliore, diventa tecnicamente un secondo validation set e la tua stima finale sarà ottimistica (falsata).codecademy+1​

Perché questa distinzione è critica per l'Embedded AI?
Dato il tuo focus su STM32 e quantizzazione, questa distinzione ha un peso ulteriore:
Validation per la Quantizzazione: Spesso si usa un subset del validation set come calibration set per calcolare i range dinamici dei tensori durante la quantizzazione post-training (PTQ) da float32 a int8.
Evaluation sul Target: L'Evaluation set è quello che dovresti far girare direttamente sul microcontrollore (tramite X-CUBE-AI o TensorFlow Lite for Microcontrollers) per verificare che l'accuratezza non sia degradata troppo rispetto al modello float originale.encord​
Consigli Pratici
Split Classico: Una suddivisione comune è 60% Training / 20% Validation / 20% Test. Se hai milioni di dati, il validation/test può essere anche molto più piccolo (es. 98/1/1).
Cross-Validation: Se hai pochi dati, invece di un validation set fisso, usa la K-Fold Cross-Validation. Addestri K volte su fold diversi e medi i risultati per avere una stima di validazione più robusta.

il fine-tuning di un modello su cosa deve essere fatto?
Il fine-tuning deve essere fatto su un set di dati specifico per il tuo nuovo task o dominio (target domain), non sui dati originali su cui il modello è stato pre-addestrato (source domain).encord​
Tecnicamente, devi trattare il fine-tuning come una "nuova fase di training in miniatura". Quindi, il dataset specifico del tuo target deve essere a sua volta suddiviso nuovamente in:
Training Set (Target): La parte più grossa dei tuoi nuovi dati. Serve per adattare i pesi del modello pre-allenato alle specificità del tuo problema (es. riconoscere suoni industriali specifici invece di suoni generici).
Cosa cambia rispetto al training da zero: Spesso si usa un Learning Rate molto più basso (es. 1e-4 o 1e-5) per non "distruggere" le conoscenze pregresse del modello.arxiv​
Validation Set (Target): Un sottoinsieme dei tuoi nuovi dati, usato per monitorare l'overfitting sul nuovo task.
Cruciale per: Decidere quando fermare il fine-tuning (Early Stopping). Se continui troppo a lungo, il modello diventa bravissimo sui tuoi pochi dati di training ma perde la capacità di generalizzare (fenomeno del Catastrophic Forgetting se si dimentica troppo del pre-training, o semplice overfitting).learn.microsoft+1​
Evaluation/Test Set (Target): Dati del nuovo dominio mai visti.
Scopo: Ti dice se il modello adattato funziona davvero nel tuo scenario reale (es. sul microcontrollore STM32).milvus​

Strategie Comuni
Feature Extraction: "Congeli" (freeze) tutti i layer tranne l'ultimo (la "testa" o classifier). Il training avviene solo sull'ultimo layer usando i tuoi nuovi dati. È veloce e richiede pochi dati, ideale per embedded.discuss.huggingface​
Full Fine-Tuning: Scongeli tutto il modello e lo addestri sui nuovi dati con learning rate basso. Richiede più dati e potenza di calcolo, ma adatta meglio le feature profonde al tuo problema.
Regola d'oro: Se il tuo dataset target è piccolo (come spesso accade in progetti embedded custom), usa la tecnica del Feature Extraction o un fine-tuning molto leggero per evitare l'overfitting immediato.

come metto da parte alcune modifiche git per poi fare pull e poi rimettere le modifiche che ho fatto ?
1. Metti da parte le modifiche
Questo comando prende tutti i file modificati (non ancora committati) e li salva in una "pila" temporanea, pulendo la tua directory di lavoro.
git stash
(Se vuoi dargli un nome per ricordarti cosa sono, puoi usare: git stash save "descrizione modifiche")
2. Fai il pull
Ora che la tua directory è pulita, puoi scaricare gli aggiornamenti dal remoto senza conflitti immediati.
git pull
3. Rimetti le modifiche
Questo comando riprende le modifiche salvate nel punto 1 e prova ad applicarle sopra il codice appena aggiornato.
git stash pop
Cosa succede se c'è un conflitto?
Se durante il git stash pop ricevi un messaggio di conflitto, significa che il git pull ha modificato le stesse righe che avevi modificato tu.
Git ti avviserà quali file sono in conflitto.
Apri quei file (es. in VS Code), risolvi i conflitti (scegliendo tra "Current Change" e "Incoming Change").
Una volta risolti, devi dire a Git che hai finito:
bash
git add nome_file_risolto
Nota: In caso di conflitto, lo stash non viene cancellato automaticamente. Se vuoi pulirlo dopo aver risolto tutto a mano, usa git stash drop.

Integrazione NNI per ottimizazione hyperparameters: (!!!)
In generale, l'ottimizzazione degli iperparametri (HPO) con NNI conviene attivarla in 3 scenari specifici all'interno del tuo grafo. Non è sempre necessaria, ma diventa fondamentale quando le "regole standard" non bastano più.
Ecco quando dovresti rispondere "nni" alla domanda del grafo:
1. Quando cambi l'Architettura del Modello
Se nel passaggio precedente (ask_and_parse_user_modifications) hai chiesto all'agente di modificare la rete (es. "Aggiungi un layer denso", "Cambia la funzione di attivazione"), i vecchi parametri di training non vanno più bene.
Perché: Una rete più profonda potrebbe richiedere un Learning Rate diverso o più epoche per convergere. NNI trova automaticamente la configurazione che fa funzionare al meglio la tua nuova architettura personalizzata.
2. Quando usi un Nuovo Dataset (specie se Sintetico)
Se stai addestrando su un dataset che non hai mai usato prima, o sui dati sintetici generati dall'AI nel passaggio precedente (generate_synthetic_samples).
Perché: Non sai a priori quanto sia "difficile" per la rete imparare da quei dati. NNI può testare diversi batch_size e ottimizzatori per trovare quello che massimizza l'accuratezza senza andare in overfitting.
3. Per l'Edge AI (STM32) - La Performance è Critica
Questo è il caso d'uso più forte per il tuo progetto. Quando devi portare il modello su un microcontrollore, ogni millimetro di performance conta.
Cosa puoi fare: Invece di ottimizzare solo l'accuratezza, puoi chiedere a NNI di cercare il compromesso migliore tra Accuratezza e Dimensione/Complessità.
Esempio: Puoi dire a NNI di cercare la configurazione di layer più piccola possibile (es. meno neuroni) che mantenga comunque un'accuratezza > 90%. Questo è difficilissimo da fare a mano.
❌ Quando NON conviene (rispondi "standard")
Prototipazione veloce: NNI lancia molti trial (es. 10, 20 o 100). Se vuoi solo vedere "se funziona" in 2 minuti, usa il fine-tuning standard.
Transfer Learning semplice: Se stai solo riaddestrando l'ultimo layer di una MobileNetV2 su dati molto simili a ImageNet, le impostazioni standard (Learning Rate basso, poche epoche) funzionano quasi sempre bene.
In sintesi: Usa NNI quando vuoi spremere il massimo delle prestazioni dal tuo modello o quando hai cambiato le carte in tavola (dati/architettura) e non sai quali parametri usare.

!! L'obiettivo del nni experiment è trovare i migliori parametri per il modello di rete neurale? vengono cambiati i parametri di ogni layer o come funziona?
L'obiettivo di un esperimento NNI (Neural Network Intelligence), nel modo in cui è configurato attualmente nel tuo progetto, è fare Hyperparameter Optimization (HPO).
Ecco la distinzione fondamentale per rispondere alla tua domanda:
Parametri dei Layer (Weights & Biases):
Questi sono i "numeri" all'interno dei neuroni (matrici di peso).
NNI NON li tocca direttamente.
Questi vengono aggiornati ("imparati") da TensorFlow/Keras durante il comando model.fit() tramite l'algoritmo di backpropagation.
Iperparametri (Hyperparameters):
Questi sono le "manopole" che controllano COME avviene l'addestramento.
NNI ottimizza questi.
Nel tuo file manager.py generato, abbiamo definito questo spazio di ricerca:
search_space = {
    'learning_rate': {'_type': 'choice', '_value': [0.001, 0.0001, 0.00001]},
    'batch_size': {'_type': 'choice', '_value': [16, 32, 64]},
}
Come funziona il flusso
Manager (NNI): Sceglie una combinazione, ad esempio 
learning_rate=0.001 e batch_size=32.
Trial 1: Lancia trial.py con quei valori.
Il modello si allena (modificando i suoi pesi interni) usando quel learning rate.
Alla fine restituisce l'accuratezza finale (es. 85%).
Manager (NNI): vede il risultato e dice "Ok, proviamo una combinazione diversa", ad esempio learning_rate=0.0001.
Trial 2: Lancia un nuovo trial.py.
Il modello riparte (o continua, a seconda della logica, ma solitamente riparte) e si allena con i nuovi parametri.
Restituisce l'accuratezza (es. 88%).

"Ensure One-Hot Labels" significa assicurarsi che le etichette (le risposte corrette) siano nel formato "vettoriale" richiesto dalla rete neurale, invece che come semplici numeri interi.
Ecco la differenza pratica:
Label "Sparse" (Intero): Se hai un'immagine di un gatto (che è la classe numero 2 su 3 possibili: cane, uccello, gatto), l'etichetta è semplicemente: 
y = 2
Label "One-Hot" (Vettoriale): La stessa etichetta viene trasformata in un vettore di zeri, con un 1 (hot) solo nella posizione corrispondente alla classe: 
y = [0, 0, 1]
 (Cane=0, Uccello=0, Gatto=1)
Perché è necessario? La tua rete neurale, nello strato finale, ha 10 neuroni (se hai 10 classi) e usa la funzione 
softmax
. Questo significa che non "sputa fuori" un numero intero (es. "2"), ma un vettore di probabilità, tipo: 
[0.01, 0.05, 0.94, ...]
Per calcolare l'errore (la Loss), la rete deve confrontare questo vettore di probabilità con l'etichetta vera. Se l'etichetta è anch'essa un vettore ([0, 0, 1, ...]), il confronto è matematicamente diretto.
L'errore che avevi prima (Shapes incompatible) accadeva proprio perché la rete si aspettava un vettore (One-Hot) per fare il confronto, ma il dataset gli stava fornendo qualcos'altro (probabilmente interi o vettori di dimensione sbagliata). Il codice che ho aggiunto converte tutto in One-Hot automaticamente, risolvendo il problema.
optimizer cosa fa? cosa cambia tra Adam e SGD ? 
L'Optimizer è l'algoritmo che "guida" l'apprendimento della rete neurale. Se immaginiamo la Loss (l'errore) come una montagna e il punto di errore minimo come la valle, l'optimizer è il metodo che la rete usa per decidere in che direzione camminare e quanto grandi devono essere i passi per arrivare a valle nel minor tempo possibile.
Ecco le differenze principali tra i due che abbiamo inserito nella search space:
1. Adam (Adaptive Moment Estimation) 🚀
È l'optimizer "moderno" e più usato oggi.
Come funziona: Adatta la velocità di apprendimento (learning rate) per ogni singolo parametro della rete. Se un parametro oscilla troppo, Adam lo rallenta; se si muove lentamente, lo accelera.
Vantaggi:
Molto veloce a convergere (arriva subito a buoni risultati).
Richiede pochissimo tuning (funziona bene con i parametri di default).
Ideale per iniziare quasi ogni progetto.
Svantaggi: A volte può "saltare" il minimo assoluto perfetto perché va troppo veloce o si adatta troppo ai dati di training.
2. SGD (Stochastic Gradient Descent) 🐢
È l'algoritmo classico, la base di tutto il Deep Learning.
Come funziona: Fa dei passi di dimensione fissa (stabiliti dal tuo learning rate) nella direzione della pendenza massima verso il basso.
Vantaggi:
Se ben configurato (con momentum), può arrivare a una precisione finale leggermente superiore ad Adam ("generalizza" meglio).
È matematicamente più semplice e stabile.
Svantaggi:
È molto più lento di Adam.
È estremamente sensibile al learning rate: se il passo è troppo grande, "rimbalza" fuori dalla valle; se è troppo piccolo, non arriva mai in fondo.
Perché li abbiamo messi entrambi in NNI?
Perché per compiti di Computer Vision (come il tuo su STM32), spesso succede che:
Adam ti porta al 75-80% di accuracy in pochi minuti.
SGD potrebbe metterci il triplo del tempo, ma magari (se trova il passo giusto) riesce a portarti all'82-83%.
NNI serve proprio a testare queste due "personalità" diverse per vedere quale si adatta meglio al tuo specifico dataset e modello!
cosa fanno model.compile e model.fit ? 
Questi sono i due "motori" principali di Keras/TensorFlow. 
Se immaginiamo che il modello sia un'automobile: 
1. model.compile() -> La "Messa a punto" 🔧 Prima di correre, devi configurare come la macchina deve comportarsi. Con compile non stai ancora allenando, stai definendo le regole matematiche: 
-Optimizer (es. Adam, SGD): È il pilota. Decide come sterzare i pesi della rete per ridurre l'errore. 
-Loss Function (es. categorical_crossentropy): È il giudice. Calcola "quanto ha sbagliato" il modello. Più il valore è alto, peggio è. 
-Metrics (es. accuracy): È il tabellone dei punteggi. Ci dice in modo comprensibile all'uomo come sta andando (es. "indovina l'80% delle foto"). In breve: Configura il modello per l'addestramento. 
2. model.fit() -> La "Gara" 🏁 
Questo è il comando che fa partire l'allenamento vero e proprio. È qui che il tempo passa e la CPU/GPU lavora: 
-Dati (train_ds): Dai il libro (i dati) al modello perché lo studi. 
-Epochs: Indica quante volte il modello deve leggere l'intero libro dall'inizio alla fine. Noi abbiamo messo 3, quindi farà tre passate complete. 
-Validation Data: Durante lo studio, ogni tanto facciamo un "esame a sorpresa" su dati che il modello non ha mai visto per vedere se sta imparando davvero o se sta solo memorizzando a memoria (overfitting). 
-Verbose: Decide quanto deve parlare il modello durante la gara (noi abbiamo messo 0, quindi sta zitto per non riempire i log di NNI). 
In breve: Esegue il ciclo di apprendimento (leggi dati -> calcola errore -> correggi pesi). 
Cosa succede nel tuo caso specifico? 
Nel tuo esperimento NNI: NNI sceglie un optimizer e un learning_rate. 
-model.compile riceve quei parametri. 
-model.fit prova ad allenare il modello per 3 epoche con quei parametri. 
-Alla fine, restituisci l'accuratezza finale a NNI per fargli capire se quella combinazione era buona o no.

IS_RETRAIN come funziona? F
IS_RETRAIN è una sorta di interruttore logico che permette di usare lo stesso file (trial.py) per due scopi diversi.
Immaginalo come una variabile che dice allo script: "Stiamo facendo un test veloce per NNI, o stiamo allenando il campione finale (con i parametri migliori) per salvarlo?"
Ecco come funziona tecnicamente nel tuo progetto:
1. Fase NNI (IS_RETRAIN = False)
Quando lanci l'esperimento, NNI chiama trial.py molte volte:
Input: Prende i parametri (LR, Batch Size, etc.) direttamente da NNI tramite  nni.get_next_parameter().
Output: Al termine dell'ultimo giro (fit), invia l'accuratezza al Web UI tramite nni.report_final_result().
Cosa NON fa: Non salva file .h5 su disco, per non riempire la memoria di modelli inutili.
2. Fase Retrain (IS_RETRAIN = True)
Una volta che NNI ha finito tutti i test, il file manager.py identifica i parametri vincenti e lancia trial.py un'ultima volta in modo speciale:
Attivazione: Il manager imposta una variabile d'ambiente (RETRAIN_MODE='true').
Input: Lo script legge i parametri "campioni" (i migliori trovati) che il manager ha passato in NNI_PARAMS.
Output: Alla fine dell'allenamento con i parametri migliori, salva finalmente il file fisico best_model.h5.
Perché si fa così?
NNI di default non salva i modelli allenati durante le prove (li usa solo per calcolare i grafici). Senza questo trucco di IS_RETRAIN, dopo aver trovato i parametri migliori nel Web UI, dovresti ri-allenare il modello a mano.
Con questo sistema, invece, alla fine dell'esperimento ti ritrovi automaticamente con il file .h5 ottimizzato pronto per essere convertito in codice C per la tua board STM32.
